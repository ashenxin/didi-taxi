## 1. 交付边界与业务分支

所有路线问答必须先在客服会话中得到乘客明确确认的起点和终点。新会话不继承地图页的起终点、路线或导航状态，也不能只凭聊天摘要猜测。客服先从本会话文字提取两端，缺少任一项时追问；两端齐全但乘客未明确确认时，复述具体地点及必要的城市、地址，等待确认。首条消息已明确确认两端、且地图可唯一确定对应地点时，本轮直接处理原始意图，不进入待确认轮次。地点有多个可能位置时先澄清，不能静默使用地图首条结果。确认前可查询地点以供澄清，但不进行驾车算路、不判断是否经过，也不列收费站方案。

| 分支 | 输入 | 结果 | 是否要乘客选择 |
| --- | --- | --- | --- |
| 普通起终点路线 | 已确认的起点、终点 | 真实地图默认路线卡片及该路线预计时间，供后续核查 | 否 |
| 核查当前路线 | 起终点、具体当前路线、指定地点 | 对这条路线回答经过、不经过或暂无法确认；不改线 | 否 |
| 查询有无经过路线 | 起终点、指定地点 | 本次条件下找到、未找到可验证路线或暂无法确认；本轮不强制出卡 | 否 |
| 指定地点规划 | 起终点、一个明确地点、乘客明确提出的通过要求 | 验证成功后直接返回一张新路线卡片及自身预计时间 | 仅地点身份歧义时澄清地点 |
| 查询可选收费站路线 | 起终点 | 展示本轮已验证的不同收费站路线方案和各自预计时间；选定后返回完整卡片 | 是，选择路线方案 |

本期不计算新旧路线时间或里程差，不跟踪乘客是否导航、下单、出行或实际到达。不能把“当前路线不经过”说成“从起点到终点不存在经过路线”。方案查询也不承诺穷尽全部收费站。

## 2. 现状与需要调整的边界

- 当前乘客叫车所调用的 /api/v1/map/route 仍由 MockRouteProvider 返回 stub 指标，与客服路线隔离。真实高德驾车适配器能够保留路线折线和导航步骤；客服默认路线服务与短时快照缓存基础类已建立，尚未接入对话编排及真实 Redis 验证。
- 现有模型可见工具 plan_route_candidates 只接收地点关键词、区域、地点类型；ToolContext 只有起终点、可选 POI 集合和结果接收器。它没有本会话当前路线输入，也没有“核查本会话路线”或“无指定收费站关键词时发现可选方案”的完整编排。
- 现有规划服务已移除参考路线差值和方向排除，验证器以导航到达事件核查实际经过；CurrentRoutePassageService 已能对传入的同一条高德路线给出经过、不经过或证据不足结论。它尚未连接客服会话和可信路线缓存，也不负责乘客归属校验；上线前仍须用真实地图样本验证各地点类型的证据强度。
- 旧的 TEST 仍包含“候选集合 → 必选 routeCandidateId → SELECTED”流程；`passenger_ai_conversation_patch.sql` 现只定义会话表和消息表，不再创建旧路线任务表。本版只有开放式收费站方案查询需要路线方案选择；指定地点规划成功后直接出卡。旧表在各环境是否已删除需分别核验。

## 3. 服务职责与数据权威

Gateway 负责乘客鉴权和可信身份头；passenger-api 负责对话编排、公开流和内部服务协调；passenger-service 负责会话、全部乘客及客服消息、消息顺序和请求幂等；map-service 负责真实地点查询、真实驾车路线、经过验证、临时确认上下文和完整路线快照的短时缓存；Spring AI Alibaba Agent 负责理解提问、必要追问和基于已验证摘要组织中文回答。passenger-service 不另存已确认地图地点或当前路线的权威状态。

地图路线、地点身份和预计时间由地图服务及确定性校验给出，不由模型填坐标、选择原始 POI 或编造分钟数。原始 POI、可信导航点和完整折线留在服务端；乘客收到适合展示的路线折线，模型只收到足以解释的摘要。

完整聊天历史由 passenger-service 保存，包括客服确认提问、乘客确认或修正回复、路线卡片及失败说明；卡片消息的 `payload_json` 只留展示所需的地点名称、`routeRef`、里程和预计时间等摘要，不保存可再次核查的完整折线与导航步骤。地图快照有效时可临时补出完整卡片；过期后只显示历史摘要。模型每轮可使用会话摘要和最近 20 条已完成消息；这些自然语言历史及展示字段不能替代地图服务中的可信地点和路线快照。map-service 不连接 passenger 数据库，也不保存长期聊天历史；短时缓存为归属校验关联可信乘客 ID 和会话编号。

同一对话继续提问所需的地图地点身份、待确认地点与原始意图、地点或路线选项，由 map-service 按可信乘客 ID、会话编号短时缓存；新会话的临时上下文为空。passenger-service 只按顺序保存对话消息，不能从模型摘要或旧消息推断过期的地图坐标。乘客首次只给出两端时，客服确认问题先写为消息，乘客的“对”或修正也写为消息；地图服务仅在仍有效的待确认上下文与当前回复相符时继续原意图。首条消息已明确确认两端且地图唯一确定身份时，本轮直接处理。乘客更改任一端时使旧路线与选项失效并重新确认。若地图临时上下文或旧路线快照过期，客服在原对话框重新询问两端；确认提问和乘客回复照常持久化，map-service 重新查询并核对地点后才规划或核查。乘客直接在新消息里重新明确确认两端且地点唯一时，按首轮明确确认规则处理。

当前短时层已包含单端点补齐、两端待确认、已确认条件、完整路线快照、地点澄清选项和收费站路线方案索引。Redis 记录最多保存 5 分钟；读取时按乘客、会话、条件版本、任务及选项成员关系核对，缺失或过期即失效。路线快照读取还必须重新取得地图服务当前已确认条件。

## 4. 具体当前路线的来源

“这条路线”仅指客服在本会话内生成并展示、地图服务快照仍有效的具体真实路线。地图页路线不进入客服；新会话没有当前路线。客服取得乘客明确确认、且已对应真实地图地点的起终点后，通过 map-service 正式内部能力生成无指定途经点的默认路线，或在指定地点规划成功后取得新路线。本会话最新一张已持久化的路线卡片对应当前路线；两种路线都可成为后续核查对象，尚未选定的开放式备选方案不自动成为当前路线。

map-service 已引入 Redis 依赖并建立短时缓存类以保存完整权威路线快照和临时会话上下文；运行环境的 Redis 连接配置仍需核验。服务端生成随机、不透明的 `routeRef`，将其与可信乘客 ID、会话编号、已确认起终点、地图提供方、GCJ02 折线、导航步骤、总里程、预计时间、路线条件与版本、生成和失效时间绑定。客服消息的展示摘要可含 `routeRef` 以重放历史卡片，但不能凭该字段恢复过期路线或作为无需鉴权的读取凭证。乘客请求只提交聊天文字，不提交路线引用或地图页状态作为可信事实。

基础快照只对应一条已选定的真实驾车路线，字段如下。`routeRef` 是快照标识；客服当前路线由本会话最新一张已持久化的路线卡片确定，不另存 `currentRouteRef` 状态字段。

| 字段组 | map-service 快照字段 | 作用 |
| --- | --- | --- |
| 引用与归属 | `routeRef`、`customerId`、`conversationNo`、`conditionVersion` | 绑定认证乘客、客服会话和本轮起终点条件；解析时核对，防止旧路线或他人路线被复用 |
| 两端地点 | `origin`、`destination`：各含服务端确认的名称、地址或城市、地图地点身份（有则保存）和 GCJ02 坐标 | 确定实际用于这次算路的两端；不凭模型补造地图地点 ID |
| 路线来源 | `provider`、`coordinateSystem=GCJ02`、`travelMode=DRIVING`、`routeKind`（`DEFAULT` 或 `VIA_PLACE`） | 标明地图来源和路线性质；本期只支持驾车，不另设步行、公交等通行方式 |
| 地图路线 | 按行驶顺序排列的完整 `polyline`、`navigationSteps` | 前者用于有效期内展示卡片；后者用于对同一条路线核查后续提问的地点。每段步骤保留 `instruction`、`action`、`assistantAction`、`orientation`、`roadName` 和该段 `polyline` |
| 数值与时效 | `distanceMeters`、`durationSeconds`、`generatedAt`、`expiresAt` | 说明本路线的里程与预计行驶时间，并限制完整快照的使用时长 |

`VIA_PLACE` 路线另存本次选定的 `via` 地点快照（地点 ID 如有、名称、地址、三类业务类型、可信导航点）、发给地图算路的有序 `routingWaypoints`，以及 Java 规则给出的 `passageVerification`（`PASSED` 和具体证据原因）。这些字段证明本次规划的指定地点要求；普通 `DEFAULT` 路线的 `via` 为 null。默认路线若作为收费站方案展示，方案关联记录另存该站点的身份和验证结果，并引用同一条完整路线。快照不预存对未来任意地点的“经过”结论，乘客后来问到 X 时，须从该快照的导航步骤和折线重新核查 X。完整折线或必要导航步骤缺失时，不能把快照当作可核查的完整路线；仅靠近地点中心坐标也不能生成 `PASSED`。

每次解析引用时，map-service 核对可信乘客 ID、会话编号、起终点条件、地图提供方和有效期；passenger-api 先核对会话归属。引用失效或缓存丢失时，旧路线不得用于核查，客服须先请乘客在同一对话里重新确认起终点；若旧卡片有指定途经点，再确认本轮是否继续使用该要求并重新解析地点，不能无声改成默认路线。之后按本轮条件生成并展示新路线；双方确认消息由 passenger-service 保存。`routeRef` 不代表已启动导航，也不单独授予读取权限。完整快照暂定 5 分钟有效；历史消息中的文字、里程和预计时间仍可回看，过期后不再展开完整折线。

## 5. 路线判断与地图证据

### 5.1 核查现有路线

passenger-api 先从本会话最新一张已持久化的路线卡片读取 `routeRef`，让 map-service 解析同一条路线快照，并用受控地点查询确认具体收费站、服务区或加油站。地图步骤、可信收费站通道或站点可通行导航点与这条路线相匹配时回答“经过”；路线证据完整且能够排除该地点时回答“不经过”；路线数据或地点身份不足时回答“暂无法确认”。已有有效路线时，核查不调用“经该地点重新算路”来替代它；本会话首次确认两端但尚无路线时，先生成并展示默认路线，再核查。旧路线或临时上下文过期时先重新确认两端，不凭历史卡片自动重建路线。

### 5.2 生成经过指定地点的新路线

先由受控地图查询确认地点身份；多个不同城市或地址的同名地点必要时先展示地点选项。服务区和加油站的“经过”至少需要路线实际到达该站的可通行导航点；乘客明确要求进入时核对可通行入口。收费站需证明路线经过可信收费站导航点或收费通道；若乘客明确说从该站上高速或下高速，再核对相应角色。仅有路线折线靠近 POI 中心点不能证明满足要求。

地图必须返回合法驾车路线及其预计时间。与旧路线相反、合法掉头、折返或绕行较远本身不构成拒绝理由；不做新旧路线方向对比和参考路线差值计算。若地图只给出地理接近而缺少实际通过证据，返回“无法验证”，不能生成成功卡片。成功后由服务端选定一条已验证路线直接出卡；若地图返回多条合法路径，可按确定性推荐规则选一条，不增加形式上的路线选择。

### 5.3 发现收费站路线方案

该分支没有用户指定的收费站关键词，不能把对单个关键词调用 plan_route_candidates 或展示收费站 POI 搜索结果当成完成需求。地图服务须从起终点的真实默认路线和受控范围内可发现的收费站候选出发，对有限数量的不同收费站尝试真实算路、验证实际经过、去重并排序。现有代码尚无这个发现能力；候选来源、搜索范围、数量上限和地图调用预算应在代码讨论时以真实地图能力验证。若无法可靠发现或验证方案，应说明本次暂无法给出方案；只验证到一个时就只返回一个，不凑数。

每个展示项包含不透明 `routeOptionId`、收费站摘要、预计时间、默认方案标记和有效期；完整路线与可选项成员关系由 map-service 绑定并短时缓存，passenger-service 只将展示给乘客的选项摘要写入客服消息。乘客选定方案时，passenger-api 核对会话归属，在数据库事务外按可信乘客、会话、条件版本和 `routeOptionId` 从 map-service 解析仍有效的完整路线；passenger-service 按既有消息幂等和顺序规则保存乘客选择与客服卡片。该选择不要求模型或高德重算。方案缓存过期或条件变化时先重新确认两端，再重新查询。地点身份澄清使用 `placeChoiceId`，是不同交互。

## 6. Agent 与工具边界

Agent 可以识别“核查当前路线／查询有无经过路线／指定地点规划／查询可选收费站路线”以及地点名称和乘客明确提出的进入、上高速、下高速要求。实际分支、地点、路线和最终结果须由服务端结构化状态确认；模型文本不是业务权威。

需要的业务能力是：核查服务端当前路线、按明确地点规划并验证、发现不同收费站可行方案。它们可以由 Agent 调用的高层工具或由编排层直接调用 Java 服务实现；不要求每个能力都暴露为一个模型工具。现有 plan_route_candidates 可复用的只是具名地点查询和算路部分，不能靠修改提示词补齐缺失的当前路线和开放式方案能力。原始 POI 查询继续留在 Java 内部，模型不得提交 POI ID、坐标、路线或结果标识。

应用通过 ToolContext 或等效可信参数注入本会话已核对的起终点、服务端当前路线引用和结果接收器；完整路线不进入模型上下文，也不由地图页或客户端提交。模型仅在地图结果已确定后生成说明。流式文字不得提前声称“经过”或报出尚未验证的时间。

## 7. 对话消息、临时上下文与 SSE

公开文字轮次仍采用两段短事务：passenger-service 的 begin 在会话行锁内核对幂等键和活动请求，再保存乘客消息、分配顺序号并占用本会话活动请求；同键并发只允许一个请求开始执行。活动请求超过接管阈值时，begin 先为旧请求落库失败客服消息并释放占用，同键重试重放该失败，不再重复调用模型和地图；不同键可在同一事务内开启新轮次。旧请求迟到的 complete 不能覆盖失败消息。模型和地图调用在事务外完成；complete 或 fail 获取会话行锁后重查同一请求的客服消息，命中时重放已有结果，否则保存客服回复、确认提问、卡片展示摘要或失败说明，并释放活动请求。乘客回复“对”、修正起终点或选择方案也各自作为本会话消息持久化。结果消息保存成功后才发送最终 SSE 内容事件；最新路线卡片一经持久化，即成为后续“这条路线”的来源。断线后可从历史或请求状态恢复；历史中的乘客消息带回原客户端幂等键，使前端在未收到 turn.started 的情况下也能精确合并本地消息并找回 requestNo。完整折线与导航步骤不写入 passenger-service。

map-service 以可信乘客 ID 和会话编号短时缓存已核对的起终点、待确认地点与原始意图及地点或路线选项；外部调用的迟到结果须按当前上下文和条件版本核对。首次只给出两端时，客服先追加确认提问；首轮已明确确认且地图唯一定位时直接处理。缓存失效或选项过期时，不靠聊天摘要恢复旧坐标或旧路线；客服可引用历史中可读的两端名称提出具体确认问题，历史不足时请乘客重新说出两端，乘客确认或修正的回复也追加到历史。随后 map-service 重新查询并核对地图地点；只有新条件明确后才重新规划或核查。若仅有“对”而没有可对应的最新确认问题，继续要求乘客说明两端。

最终内容事件仍分为 answer.completed、route.card、route.options、place.choices，一轮最多一类；失败发送 turn.failed。相同幂等键重放已落库的失败轮次时，按原失败码和乘客可读说明发送 turn.failed，不发送成功内容事件或 turn.completed，也不重新调用模型和地图。路线卡以 payload.routeCard 保存无折线摘要；兼容旧版平铺 payload。重放时 BFF 仅从已归属校验的卡片消息取得 routeRef，调用 map-service 内部 replay 接口，后者按当前已确认条件、乘客、会话和快照有效期复核后返回完整路线；缓存或当前条件失效时 BFF 以 payload.routeCard 返回落库摘要并标记 expired，不从文字重建地图事实。route.options 与 place.choices 的 taskNo、选项成员和有效期由 map-service 的短时缓存管理，不要求 passenger-service 持久化路线任务。乘客选择时先由 map-service 核对归属、条件版本和有效期；passenger-service 仅按现有会话幂等和消息顺序规则追加选择及客服结果。旧选项失效则重新确认两端并重新查询。单会话活动请求、消息幂等和迟到结果隔离仍须保留。

## 8. 既有 SQL 与最简落库范围

本期只使用现有 `passenger_ai_conversation` 保存会话、消息顺序、幂等与活动请求，使用 `passenger_ai_message` 保存乘客与客服的全部对话及卡片展示摘要。消息归属经 `conversation_id` 关联会话并校验 `customer_id`，消息表不再冗余保存乘客 ID；已有消息表须单独执行 `passenger_ai_message_drop_customer_id_patch.sql`，只改建表脚本不会删除旧列。现有消息表已有 `content` 和 `payload_json`；展示摘要可存地点名称、`routeRef`、里程、预计时间和失效标记，但不能成为地图事实的权威来源。旧 `passenger_ai_route_task` 的候选快照和必选路线流程不再纳入本期 SQL；完整地图路线只在 map-service 短时缓存，不另建持久化路线快照表。

除移除消息表冗余 `customer_id` 的独立迁移外，当前没有确定的新增列需求；消息类型与 payload 语义由实现和文档约定，落地前仍须核对实际环境的列宽、约束和历史兼容性。若后续发现现有表无法满足明确的业务约束，再针对该差距提出最小增量迁移。`CREATE TABLE IF NOT EXISTS` 不会升级已经存在的表；更新 SQL 文件中的列注释也不会修改已建表的注释。旧路线任务表的删除须独立执行，本脚本不会删除它。

## 9. 安全、时效与失败

- 公开接口经 Gateway 和 passenger-api；Gateway 移除客户端伪造的 X-User-Id 后按认证结果注入身份。内部调用使用 X-Internal-Service-Token，贯穿 X-Request-Id；map-service 不接收手机号。
- 会话、内部当前路线引用、地点选项和收费站路线选项均按认证乘客核对。归属不符按不存在处理。客户端只提交聊天文字及其主动选择的 placeChoiceId 或 routeOptionId，不能提交起终点结构、路线引用、导航步骤或折线作为客服事实。
- 当前路线和方案的完整快照有效期暂定 5 分钟。过期历史仅保留文字、里程和预计时间，不再展开完整折线或继续核查旧路线；需要继续路线问答时，先在原会话追加客服重新确认两端的提问，保存乘客回复，再按新确认的条件生成并展示本轮路线。
- 模型或地图超时、限流、地点不存在、路线不可达、经过证据不足须分开返回；模型调用异常按模型服务故障返回友好提示，不转成缺少起终点的追问；没有结果时不由模型补造地点、路线或时间。
- 1 秒内反馈受理，正常请求端到端 P95 目标 15 秒，单轮执行上限 60 秒；SSE 连接上限和心跳需覆盖执行时间。模型循环、地图调用和用户频率设置上限，具体预算在实现前核定。
- 日志只记录请求号、工具、耗时、验证结论和脱敏错误；不记录密钥、完整聊天正文或完整位置历史。

### 9.1 当前时长与调整入口

| 时长 | 当前值与代码入口 | 生效方式 |
| --- | --- | --- |
| 会话活动请求接管 | `passenger.ai.turn-stale-seconds` 默认 60 秒，`AiConversationService` | 从 `activeRequestStartedAt` 计算；仅在后续 `begin` 取得会话行锁时写入旧轮次失败并允许不同键接管，不是后台定时清理。同键重试只重放旧失败，迟到 complete 不得覆盖。 |
| 地图短时上下文 | 最多 5 分钟，`PassengerRoutePendingConfirmationCache`、`PassengerRoutePartialEndpointCache`、`PassengerRouteConditionsCache`、`PassengerRouteSnapshotCache`、`PassengerRoutePlaceChoiceCache`、`PassengerRouteOptionCache` 及 `PassengerDefaultRouteService` | 各记录从自身生成时间计算失效时间；Redis TTL 和读取时的失效校验共同生效，读取不续期。地点选项、路线方案的有效期还不得晚于它们依赖的已确认条件或路线快照。 |
| SSE 连接 | `SSE_TIMEOUT_MILLIS` 为 60,000 毫秒，`PassengerAiConversationController` | 从建立 `SseEmitter` 开始计时；连接超时只结束流，不会取消线程池中的轮次。结果仍按消息持久化，乘客可通过历史消息恢复。 |

调整单轮执行时间时，应同时核对活动请求接管阈值、SSE 连接超时和下游模型／地图调用预算，避免正常运行的旧轮次被新请求接管或在完成前断流。当前活动请求与 SSE 均为 60 秒，边界没有额外余量；若延长处理上限，SSE 超时应覆盖处理时间并留出传输余量。调整地图有效期时，应同时修改生成失效时间、缓存写入上限、读取校验及依赖记录的有效期约束；5 分钟从各记录生成时分别起算，不随 SSE 断开或会话继续而延长。旧的 `WaypointRoutePlanningService` 候选缓存也独立使用 5 分钟，改动该能力时需一并核对。

## 10. 后续讨论顺序

map-service 的短时缓存基础类和真实默认路线服务已实现，仍需核验运行环境 Redis 连接并接入对话编排。长期会话持久化实现、新测试类和 TEST 文档留待短时层代码审阅后处理。现阶段不以旧 routeCandidateId 必选流程扩展实现；消息表冗余列迁移之外不预设其他 SQL 增量迁移。
