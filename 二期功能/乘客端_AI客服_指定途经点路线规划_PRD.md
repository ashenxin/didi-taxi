## 1. 背景与目标

乘客除了关心起点和终点，也可能要求途中经过某个高速收费站、进入某个服务区休息，或进入某个加油站。普通起终点算路无法直接表达这些要求。

本功能允许乘客用自然语言描述途经要求。系统补齐必要信息，查询真实地点，规划并验证路线，再通过地图和路线卡片呈现结果。

核心用户问题：

> “规划一条经过 XX 高速收费站／加油站／服务区的路线。”

产品目标：

1. 乘客能够以对话方式确定起点、终点和指定途经地点。
2. 结果能够说明途经条件是否满足，以及相对于普通路线增加或减少的里程、时间。
3. 地点、路线与数值具有业务数据来源；无法确认时明确告知。
4. 异常不会自动忽略用户条件，也不会影响已有普通叫车流程。

## 2. 已确认事项与草案假设

### 2.1 已确认

- 本次开发优先级为 P0。
- 先开发指定途经点功能。
- 使用 Spring AI Alibaba 构建乘客端 Agent 智能客服。
- 费用透明问答属于后续功能，本 PRD 不展开订单费用对比。
- 每步开发修改须单独获得用户同意，禁止一次性新增大量代码。

### 2.2 本草案采用的建议范围

以下是为了形成可评审文档提出的建议，不视为用户已经确认：

| 决策 | 草案建议 | 影响 |
| --- | --- | --- |
| 首期闭环 | 下单前路线查询与预览 | 首期不将路线写入订单，不向司机承诺执行 |
| 途经点数量 | 每次 1 个明确地点 | 多个地点时让乘客先选择本次要规划的一个 |
| 地点范围 | 收费站、加油站、服务区 | 不包含景点串联等通用行程规划 |
| 交互方式 | 文本对话、地点选择卡片、路线地图 | 语音输入后续评审 |
| 地图数据 | 建议接入真实地图查询和算路 | 需要评审外部地图接入范围、账号能力及配额 |
| 预估车费 | 首期可选增强项 | 计价口径未批准前，只展示里程和预计时间 |

若用户要求首期支持“使用该路线下单”，需将第 10 节扩展范围纳入定版 PRD 后再实施，不能仅增加一个下单按钮。

## 3. 用户与使用场景

目标用户为已登录的乘客。

| 场景 | 示例 | 系统应完成的行为 |
| --- | --- | --- |
| 指定收费站 | “从 A 到 B，走 XX 收费站上高速。” | 明确收费站位置与上高速方向，规划通过对应入口的路线 |
| 指定服务区 | “去 B 的路上想进 XX 服务区休息。” | 识别服务区方向，规划可进入该服务区的路线 |
| 指定加油站 | “从 A 到 B，途中到 XX 加油站。” | 确认具体站点，规划到达站点可通行入口的路线 |
| 沿用页面信息 | 起终点已选好，输入“经过 XX 服务区” | 展示并沿用当前起终点，不重复要求输入 |
| 修正要求 | “换成另一个方向的服务区。” | 更新途经地点，旧结果失效，重新规划 |
| 信息不完整 | “帮我规划一条经过 XX 的路线。” | 补齐起终点，查询 XX 的真实候选地点 |

## 4. 功能范围

### 4.1 建议纳入首期

- 智能客服中的路线规划入口及示例提示。
- 识别起点、终点、途经点名称、地点类型和明确表达的方向要求。
- 多轮补齐信息，支持乘客修改或取消本次规划。
- 查询地点候选并处理同名、地址和上下行方向歧义。
- 单个指定途经点的驾车路线规划。
- 途经要求验证、路线地图展示、距离及时间展示。
- 在数据齐备时与不带该途经约束的参考路线比较。
- 查无结果、条件冲突、无法验证、超时等异常处理。
- 用户隔离、访问控制、调用限额与功能开关。

### 4.2 首期建议不包含

- 多途经点排序和全局最优路线搜索。
- “随便找一家加油站”等未指定地点的沿途推荐。
- 行程中修改路线、修改目的地及司机导航。
- 自动创建、取消或修改订单。
- 判断司机实际是否绕路、是否真实到达途经点。
- 实际停车时长计费、高速费结算及收费规则改造。
- 历史订单费用透明问答、退款和赔付。

## 5. 页面与交互

### 5.1 入口与上下文

建议在乘客叫车页起终点区域附近提供“指定途经地点”入口，进入智能客服的路线规划场景。

- 若已有起终点，进入时展示“从 A 到 B”的摘要，允许修改。
- 页面没有起终点时，客服引导补齐。
- 定位不可用时支持手动选择地点，不阻断规划。
- 对话中的新地点与页面已有信息冲突时，展示变更后的摘要，不静默覆盖已选路线。
- 首期建议仅保留本次会话上下文；跨会话记忆与聊天记录长期留存另行评审。

### 5.2 主流程

1. 乘客输入途经要求。
2. 系统识别意图，整理已知条件并补齐缺失信息。
3. 系统查询地点候选；存在歧义时展示选择卡片。
4. 乘客完成必要选择后，系统展示当前起终点、途经地点和通过方式。
5. 信息完整且无歧义时自动开始规划，无需再增加重复确认。
6. 系统校验返回路线是否满足条件。
7. 展示路线地图、路线卡片和参考路线差异；无法满足时解释原因。
8. 乘客可查看详情、修改地点或重新规划。

### 5.3 地点候选卡片

至少展示：地点名称、类型、地址或行政区、可取得的行驶方向信息和地图位置。

- 同名但不同城市、不同道路方向的地点不能合并为一个选项。
- 仅一个高匹配候选且没有方向歧义时，可以自动选中并在摘要中展示。
- 存在实质歧义时必须由乘客选择，模型不得凭名称猜测坐标。
- 候选不符合要求时支持继续补充城市、道路或完整名称。

### 5.4 路线结果卡片

| 内容 | 展示要求 |
| --- | --- |
| 起终点与途经点 | 与本次确认的地点一致 |
| 路线地图 | 展示真实返回的路线折线、起终点及途经标记 |
| 条件结果 | 明确区分满足、不满足、无法验证 |
| 总里程与预计行驶时间 | 来自地图结果，单位明确 |
| 与参考路线的差异 | 展示增加或减少的里程、时间；无参考数据则不展示数值 |
| 生成时间 | 帮助用户理解结果时效 |
| 操作 | 查看路线详情、修改条件、重新规划 |

仅在确认进入服务区或加油站的路线后，才可使用“途经 XX 服务区／加油站”的肯定描述。路线预计时间默认不包含用户未指定的休息或加油停留时间，应在有停留意图时提示。

首期路线预览建议使用“推荐路线”“预计”等表述，不出现“司机一定按此路线行驶”的承诺。

## 6. 路线业务规则

### 6.1 “经过”的语义

| 地点类型 | 规则 |
| --- | --- |
| 收费站 | 区分从该站上高速、下高速或途中通过；存在会改变算路结果的歧义时追问 |
| 服务区 | “进去休息”等表达视为进入服务区；只说“经过”且存在路过或进入的歧义时追问 |
| 加油站 | “去加油”“到加油站”等表达视为到达站点；不能把附近主路视为已到达 |

地点选择不等于经营状态确认。没有可靠营业信息时，不承诺加油站营业、油品有货或服务区设施可用。

### 6.2 地点与方向

- 地点标识、坐标和入口信息须来自可信地图服务或经核实的业务数据。
- 同名服务区上下行两侧应按不同可达地点处理。
- 如必须绕行、掉头或离开高速才能到达，需在结果中提示，并反映相应里程和时间。
- 无法确认正确入口或行驶方向时，结果为“无法验证”，不能标记满足。

### 6.3 硬性条件与冲突

- 用户明确指定的途经地点属于硬性条件，不能为缩短路线而自动删除。
- “经过某高速收费站”与“不走高速”等要求发生冲突时，应说明冲突并由乘客调整。
- 用户提出超出首期能力的限制时，说明当前支持范围，不能假装已应用该限制。
- 替代地点或无途经点路线只能作为明确标注的备选，不能替代原要求展示为成功结果。

### 6.4 满足条件的证据

- 需要地图算路结果及可信的入口、路段、方向等信息共同支撑。
- 对进入站点的要求，应验证路线能连接对应车辆入口；对收费站，应验证通过相应路段及方向。
- 不能仅以路线折线接近地点中心坐标作为成功依据。
- 技术方案需说明各类型的可验证范围；缺少足够信息的类型不得以“已验证”上线。
- “规划路线满足要求”不代表车辆未来一定实际到达该地点，也不代表道路临时状态永久不变。

### 6.5 参考路线与时效

- 参考路线使用相同起终点、相同可用出发时间及其余偏好，仅移除指定途经点约束。
- 路线对比由后端计算，正负差值均按实际结果展示。
- 参考路线不可用时，可以展示合格的途经路线，提示“暂无法提供绕行对比”。
- 修改起点、终点、途经点或方向后，旧结果立即标记失效并重新规划。
- 新旧请求并发返回时，只将最新请求结果作为当前方案，避免旧路线覆盖新要求。
- 建议结果有效期为 5 分钟，待评审；过期后保留查看并提示重新规划。

## 7. 费用展示边界

首期建议以里程与时间为核心交付，预估车费作为待确认增强项。

若批准加入预估车费，必须满足：

1. 金额由计价服务基于该候选路线计算，模型不得自行计算或编造。
2. 明确标注“预估”，不能展示为最终账单或保证成交价。
3. 基准路线与途经路线的费用比较采用相同计价口径。
4. 高速费若仅是地图提供的估算，应独立标注其来源及是否包含在车费内；未确定收费口径前不并入订单金额。
5. 无法取得费用时，仍可展示路线，费用显示“暂无法估算”，不填 0 元。
6. 当前结算存在 mock 指标；不能将真实地图的预览估算静默写入既有 mock 结算链路。

示例文案仅作格式参考，数值由业务结果填充：

> 已找到可进入 XX 服务区的路线，预计行驶 X 公里、Y 分钟，较参考路线增加 Z 分钟。预计时间不包含您在服务区的停留时间。

## 8. 异常与降级

| 情况 | 产品行为 |
| --- | --- |
| 起终点缺失 | 引导补充，保留已明确的途经要求 |
| 地点查无结果 | 请用户补充名称或区域，不编造地点 |
| 同名或上下行歧义 | 展示候选供选择 |
| 地点可查询但无法算路 | 说明暂未找到可达路线，允许更换地点 |
| 路线无法验证途经条件 | 标记无法验证，不作为满足条件的推荐路线 |
| 用户条件冲突 | 说明冲突，等待调整后重新规划 |
| 地图或模型超时、限流 | 明确失败状态，支持重试；不无限循环调用 |
| 模型解析出错或输出无效 | 不触发不合法工具调用；允许用户重新描述或手动选点 |
| 参考路线失败 | 展示已验证的途经路线，绕行差异标记不可用 |
| 地图展示失败 | 提示地图加载失败，保留可核实的路线摘要与重试入口 |
| 计价失败 | 路线可继续展示，费用标记不可用 |
| 登录失效 | 引导重新登录，不泄露其他用户的会话内容 |
| 用户修改条件或取消 | 旧请求不得覆盖当前结果；停止不必要的后续处理 |

关闭 AI 功能或其依赖不可用时，既有普通叫车入口仍应可用。

## 9. 非功能要求与验收指标

以下性能数字为草案目标，需结合地图配额、模型及测试环境评审。

| 维度 | 草案要求 |
| --- | --- |
| 反馈速度 | 提交后 1 秒内显示受理或处理中状态 |
| 完整响应 | 信息完整、外部服务正常的请求，端到端 P95 不超过 15 秒；超过 30 秒结束本次等待并支持重试 |
| 调用控制 | 设置模型调用次数、地图调用次数、总执行时间及用户频率上限，具体数值在技术评审确定 |
| 数据依据 | 验收样本中的地点、路线和数值均可追溯，不得出现虚构地点或数值 |
| 条件遵守 | 验收样本中不允许静默丢弃硬性途经条件 |
| 隔离 | 用户身份由认证上下文确定；客户端传入会话标识不能访问其他用户数据 |
| 信息最小化 | 仅提供路线任务必要的位置和文本信息给模型，不附带手机号、支付信息或无关历史订单 |
| 指令边界 | 用户输入、POI 文本不能改变服务端权限或开放未授权业务工具 |
| 可观测性 | 可追踪请求、地点消歧、地图调用、校验状态、耗时和错误原因；日志避免记录密钥与完整敏感位置历史 |
| 发布控制 | 支持按环境或用户范围启用，能够关闭该功能并恢复普通出行入口 |

验证成功率需单独统计“符合能力范围且信息完整的请求”；缺少信息、无真实可达路线与服务故障分开统计，不用模糊的总成功率掩盖问题。

## 10. 若首期接入下单，必须补充的范围

以下能力目前属于待确认扩展，不计入建议的路线预览首期：

- 用户主动选择路线并确认下单，客服不能自行发起订单。
- 下单前重新验证路线有效性及报价变化，并展示发生变化的内容。
- 保存可追溯的已选路线、途经要求、计价输入及数据来源；是否建表由技术方案评审决定。
- 乘客订单详情和司机端展示一致的途经要求，派单、改派后不能丢失。
- 定义司机是否接受停靠、允许停留时长、额外费用及无法执行时的处理方式。
- 与现有订单幂等、状态机、取消和结算快照规则兼容。
- 明确从 mock 地图及计费指标向真实数据过渡的范围，不改变历史订单的冻结口径。

## 11. 验收用例

所有成功用例使用可核实的地图数据；mock 用于异常和边界测试时必须标识，不能证明真实道路可达。

| 编号 | 输入或条件 | 预期结果 |
| --- | --- | --- |
| AC-01 | 页面已有 A、B，用户指定一个唯一收费站及通过方向 | 沿用起终点，得到经验证的路线和地图 |
| AC-02 | 缺少起点或终点 | 补齐信息后继续，已输入条件不丢失 |
| AC-03 | 存在不同城市的同名地点 | 要求选择或补充区域，不自动猜测 |
| AC-04 | 同名服务区有上下行两侧 | 正确区分方向；无法确认时不宣称满足 |
| AC-05 | 用户要求进入加油站，路线仅从附近主路通过 | 不能判定为满足 |
| AC-06 | 用户要求经某收费站上高速 | 验证对应入口方向，不能用从该站下高速的路线替代 |
| AC-07 | 地点不存在 | 明确查无结果，不提供虚构坐标 |
| AC-08 | 地点存在但当前无可达路线 | 明确失败，可调整地点；不忽略约束 |
| AC-09 | 条件彼此冲突 | 说明冲突并等待用户调整 |
| AC-10 | 一次要求多个途经点 | 按首期范围提示先选一个，不悄悄截断 |
| AC-11 | 已生成路线后修改终点或途经点 | 旧方案失效，展示新方案 |
| AC-12 | 上一次请求晚于新请求返回 | 旧结果不覆盖新条件和新结果 |
| AC-13 | 参考路线不可用 | 保留合格途经路线，不编造差值 |
| AC-14 | 结果超过有效期 | 提示重新规划，不继续标为最新结果 |
| AC-15 | 模型或地图超时、限流 | 有明确失败及重试入口，无无限等待 |
| AC-16 | 用户取消规划 | 不继续展示为成功，不修改或创建订单 |
| AC-17 | 用户伪造其他会话标识 | 无法读取或覆盖其他用户信息 |
| AC-18 | 用户或 POI 文本要求绕过权限、忽略业务约束 | 不执行越权工具或丢弃途经要求 |
| AC-19 | 关闭功能开关 | 普通叫车流程仍可使用 |
| AC-20 | 预估车费增强项获批后计价失败 | 路线仍可展示，费用明确不可用 |

定版后须补齐各支持地点类型的真实成功案例、方向歧义案例和不可达案例，并记录验证证据。AC-20 仅在费用增强项纳入首期时适用。

## 12. 当前项目基础与开发约束

### 12.1 当前基础

- 当前地图路线请求仅包含起点和终点。
- 现有高德驾车适配代码只提取首条路线的距离和时长，需要另行设计地点查询、途经点、路线展示及验证能力。
- 现有完单结算 PRD 采用本地 mock 规划距离与 mock 计费时长，本 PRD 不直接覆盖其规则。
- 根 POM 与 XXL-JOB 模块的 Boot 版本已调整；微服务子模块依赖尚未全部对齐，不能认定整体升级验收完成。

### 12.2 服务职责约束

- Agent 负责理解、必要追问、调用业务工具和解释结果。
- 地图服务负责地点查询、算路与路线事实；具体校验职责在技术方案中落实。
- 计价服务负责金额计算；订单服务负责订单状态与冻结快照。
- 乘客请求经过现有网关及乘客端 BFF 的认证边界。
- PRD 不预设新增数据库表、服务模块、接口路径或 Java 类名，这些分别评审。

### 12.3 逐步实施方式

建议顺序为：PRD 定版 → 依赖升级验证 → 地图能力验证 → 接口与数据设计 → 单个工具实现 → Agent 编排 → 乘客端交互 → 回归验收。

每次实施前列出要新增或修改的文件、目的、范围和验证方法；用户同意后仅执行该批次。出现必须扩大范围的兼容问题时，先报告原因及具体变更，再取得同意。服务启动、停止和重启仍由用户明确授权。
