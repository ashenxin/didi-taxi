## 1. 背景与目标

地图应用通常已根据起点和终点给出一条默认或推荐路线，乘客按这条路线出行时无需使用 AI 客服。地图页与 AI 客服隔离：进入客服时不传入地图页的起终点、路线或导航状态。乘客需要加油、想避开拥堵路段等原因时，在客服对话里重新说明起终点和需求，由客服建立自己的路线。接人也是这类需求的动机，但接人地点不在本期支持的地点类型内。地图给出的路线是当时条件下的推荐结果，不能称为始终最优。

所有路线问答先在客服会话内明确并由乘客确认起点和终点。首条消息已明确确认两端、且地图可唯一确定对应地点时，本轮可直接处理原始路线需求，无需再等一条“对”。乘客可以核查客服已生成的一条具体路线是否经过某地，再在同一对话中要求规划经过该地的新路线；也可以直接询问给定起终点之间有哪些可行的收费站路线方案，选择其中一个后取得路线卡片。客服会话内尚无路线时，确认两端后先生成并展示一条真实默认路线，才可将其作为“这条路线”的核查对象。

核心用户问题：

> “当前这条路线经过五常收费站吗？”
>
> “帮我规划一条经过五常收费站的路线。”
>
> “从德清到西溪湿地可以经过哪几个收费站到达？”

产品目标：

1. 乘客核查当前路线是否经过指定地点时，AI 客服只针对这条具体路线给出有依据的结论；该轮问答结束后仍可在同一对话继续提出规划需求。
2. 乘客要求经过指定地点的新路线时，AI 客服确认地点和乘客明确提出的通行要求，返回一张确实经过该地点的路线卡片，并说明这条路线预计需要的时间；地点身份有歧义时先澄清。
3. 乘客询问给定起终点有哪些收费站路线可选时，AI 客服展示本次已验证的不同路线方案；乘客选中一个有效方案后，返回该方案的完整路线卡片和说明。
4. 地点、路线与数值具有业务数据来源；无法确认时明确告知。
5. 异常不会自动忽略用户条件，也不会影响已有普通叫车流程。

## 2. 已确认事项与草案假设

### 2.1 已确认

- 本次开发优先级为 P0。
- 先开发指定途经点功能。
- 使用 Spring AI Alibaba 构建乘客端 Agent 智能客服。
- 费用透明问答属于后续功能，本 PRD 不展开订单费用对比。
- 每步开发修改须单独获得用户同意，禁止一次性新增大量代码。
- 2026-09-17 用户补充了连续对话意图：先核查当前路线是否经过指定地点，再按需规划经过该地的新路线；也可询问可选的收费站路线方案，选择方案后获得路线卡片。规划时若地点身份不明确，应先澄清具体地点。
- P0 地点类型限定为收费站、服务区、加油站；接人等其他地点暂不纳入。
- 所有路线问答必须先明确起点和终点；新路线只说明自身预计行驶时间，不要求与原路线计算时间或里程差；交付路线卡片与说明即完成本期功能，不跟踪乘客是否实际出行。
- 地图页与 AI 客服的路线状态隔离。新客服会话不继承地图页的起终点、路线和导航状态；首次只给出两端、未明确确认时，客服复述并等待确认。若首条消息已明确确认两端，且地图能唯一确定具体地点，则本轮直接处理原始意图。同一客服会话可沿用已确认条件及客服生成的路线。
- `passenger-service` 持久化同一对话框中的乘客消息、客服提问和回复、路线卡片的展示摘要；地图服务短时保存可核查的路线及上下文。缓存失效后，客服可复述历史消息中可读的起终点名称请乘客重新确认；若历史不足以说明两端，则请乘客重新说出完整起终点。这次客服提问和乘客回复仍作为本会话消息保存。
- 新路线须由地图证明实际经过乘客指定的收费站、服务区或加油站。无需比较新路线与旧路线是否方向相反，也不因合法绕行、掉头或折返本身否决路线；若乘客明确要求从某站上高速、下高速或进入某站点，仍须核对该明确要求是否满足。

## 3. 用户与使用场景

目标用户为已登录的乘客。

| 场景 | 示例 | 系统应完成的行为 |
| --- | --- | --- |
| 默认路线 | 在客服里问“帮我规划一条从 A 到 B 的路线。” | 客服先复述 A、B 并请乘客确认；确认后用地图生成并展示当时的默认或推荐路线，将其作为本会话当前讨论路线 |
| 当前路线核查 | 客服此前展示的默认路线经三墩收费站，乘客问“这条路线经过五常收费站吗？” | 只核查客服此前展示的三墩方案，回答五常收费站是否在这条路线上；回答“不经过”时不自动改线 |
| 指定收费站改线 | “帮我规划一条经过五常收费站的路线。” | 明确起终点和具体收费站，验证新路线实际经过后返回路线卡片和该路线预计时间 |
| 查询收费站路线方案 | “从 A 到 B 可以经过哪几个收费站到达？” | 查找已验证、经不同收费站的可行路线方案，展示默认方案和其他方案供乘客选择；选定后返回完整路线卡片 |
| 指定服务区 | “去 B 的路上想进 XX 服务区休息。” | 确认具体服务区，规划实际到达其可通行入口的路线 |
| 指定加油站 | “从 A 到 B，途中到 XX 加油站。” | 确认具体站点，规划到达站点可通行入口的路线 |
| 查询有无经过路线 | “从 A 到 B 有没有经过 XX 服务区的路线？” | 查询当前条件下有无可验证的经过路线，只回答查询结论；与“当前这条路线是否经过”分开 |
| 同一对话继续规划 | 先询问是否经过，接着说“帮我规划一条经过 XX 服务区的路线” | 沿用已确认的起终点和地点条件，继续完成规划并返回路线卡片与预计时间说明 |
| 地点身份歧义 | “从 A 到 B，必须经过 XX 服务区”，查询到多个同名或近似地点 | 先澄清乘客指的具体地点，再验证；这与选择多条收费站路线方案是两种不同交互 |
| 沿用客服会话条件 | 在客服里已确认起终点，接着说“经过 XX 服务区” | 沿用本会话已确认的起终点，不重复要求输入 |
| 地图页与客服隔离 | 乘客在地图页已选好 A、B，首次进入客服只说“经过 XX 服务区” | 客服不读取地图页的 A、B，先追问起点和终点 |
| 起终点确认 | 乘客首次在客服里说“从 A 到 B”，或在会话中改成“从 C 出发” | 客服复述待使用的完整起终点，等待明确确认；未确认前不查询路线是否经过、不规划或列方案 |
| 首轮明确确认并指定途经点 | “我确认从 A 到 B，必须经过 XX 收费站，帮我规划。” | 地图能唯一确定两端和 XX 时，本轮直接验证并返回经过 XX 的路线卡片与预计时间；不先生成默认路线，也不要求再次确认或选择路线 |
| 首轮明确确认并问当前路线 | “我确认从 A 到 B，这条路线经过 XX 收费站吗？” | 若客服会话尚无路线，本轮先生成并展示默认路线，再核查这条路线是否经过 XX；不自动规划经 XX 的新路线 |
| 缓存失效后继续提问 | 旧路线卡片已过期，乘客又问“这条路线经过 XX 吗？” | 客服说明旧路线无法继续核查，提醒乘客重新确认起点和终点；旧路线若有指定途经点，还需确认本轮是否继续要求经过该点。按新条件生成并展示路线后再核查，双方确认过程保留在原对话框历史中 |
| 修正要求 | “换成另一个方向的服务区。” | 更新途经地点，旧结果失效，重新规划 |
| 信息不完整 | “帮我规划一条经过 XX 的路线。” | 补齐起终点，查询 XX 的真实候选地点 |

## 4. 功能范围

### 4.1 首期范围

- 智能客服中的路线规划入口及示例提示。
- 所有路线意图都先在客服会话里取得乘客对起点和终点的明确确认；首条消息已明确确认且地点可唯一确定时可直接处理。客服生成并展示的真实路线才可作为后续“这条路线”的核查对象，不接收地图页的起终点或当前路线。
- 识别起点、终点、途经点名称、地点类型和乘客明确表达的上高速、下高速或进入要求。
- 区分“当前路线是否经过”“给定起终点有无经过路线”“必须经过指定地点并重新规划”“有哪些收费站路线方案”四种意图，并在同一对话中连续处理。
- 多轮补齐信息，支持乘客修改或取消本次规划。
- 查询真实地点；地点身份不明确时展示可理解的地点候选，由乘客确认所指地点，选择过期后重新查询。
- 对乘客选定或唯一明确的地点，验证地图路线确实到达对应的可通行导航点；乘客明确要求进入服务区或加油站时，验证到达该站可通行入口。无须拿旧路线方向排除合法的新路线。
- 单个指定途经点的驾车路线规划。
- 收费站路线方案查询：展示本次已验证的若干不同单点方案及默认方案；乘客在有效期内选择一个方案，再返回该方案的完整路线卡片。
- 核查类需求给出有依据的结论；规划或选定方案后返回路线卡片、地图、距离、时间和文字说明。
- 规划成功时说明新路线预计行驶时间；不要求计算与旧路线或默认路线的时间、里程差。
- 查无结果、条件冲突、无法验证、超时等异常处理。
- 用户隔离、访问控制、调用限额与功能开关。

### 4.2 首期不包含

- 多途经点排序和全局最优路线搜索。
- “随便找一家加油站”等未指定地点的沿途推荐；收费站路线方案查询仅限本期定义的收费站场景。
- 接人地点等三类地点以外的任意具名途经点规划。
- 穷举给定起终点之间的全部收费站或全部可行路线。
- 将乘客选中的预览路线写入订单或启动导航。
- 行程中修改路线、修改目的地及司机导航。
- 自动创建、取消或修改订单。
- 判断司机实际是否绕路、是否真实到达途经点。
- 实际停车时长计费、高速费结算及收费规则改造。
- 历史订单费用透明问答、退款和赔付。

## 5. 页面与交互

### 5.1 入口与上下文

建议在乘客叫车页起终点区域附近提供“指定途经地点”入口。该入口只负责打开智能客服，不传递地图页已选地点、路线折线或导航状态。

- 新客服会话没有默认起终点或路线，乘客须在对话中说明；缺少任一项时客服追问。
- 当本会话第一次得到完整起终点，而乘客尚未明确确认两端时，客服先以文字复述两个具体地点及必要的城市、地址，请乘客确认；确认前不调用驾车算路、不核查是否经过，也不列收费站方案。若首条消息本身已明确确认两端，且地图可唯一确定对应地点，本轮即视为确认并处理原始意图，不再追问“对吗”。无论哪种表述，地点名称对应多个位置时都先澄清具体位置，不静默选择地图首条结果。
- 同一会话的后续需求在地图服务短时上下文仍有效时沿用已确认起终点，不逐轮重复确认；缓存失效后须重新确认两端。乘客更改任一端时，复述更新后的完整起终点并重新等待确认，旧路线及受影响的方案失效。
- 客服在本会话生成并展示一条具体路线后，才可将其作为后续“这条路线是否经过”的核查对象；这条路线可以是默认路线或经指定地点的新路线。仅凭起终点文本不能猜测一条具体路线。
- 同一客服会话内的追问沿用已确认条件；乘客在对话中修改起点、终点或途经地点时，更新条件并使受影响的旧结果失效。
- 客服新展示的路线卡片成为本会话后续“这条路线”的默认核查对象；只查询或展示尚未选定的备选方案，不替换这一对象。
- 地图页的导航状态始终独立，客服展示路线卡片不启动导航，也不修改地图页路线。
- 同一个对话框内完成一轮“是否经过”的回答后，乘客可继续提出规划要求；已确认的起终点和地点信息可以沿用，过期的查询和路线结果必须重新核验。
- 同一对话框内应保持仍有效的已确认条件和连续问答上下文。乘客消息、客服的确认提问与回复、路线说明均通过 `passenger-service` 持久化；历史卡片保留文字、里程和预计时间。完整折线仅在地图服务的短时路线快照有效时可展开；过期后历史不再提供完整地图，也不凭旧对话文字恢复可信地点或路线，客服需重新询问并保存确认对话。
- 入口样式参考高德地图：起终点区域附近的胶囊或卡片式入口；进入后为全屏智能客服会话页（样式参考见 5.5）。

### 5.2 对话主流程

1. 先在客服会话里收集起点和终点；缺少任一项时先追问。两端齐全但乘客未明确确认时，客服复述具体地点并等待确认；首条消息已明确确认两端且地图可唯一确定地点时，本轮直接处理。有同名地点时先澄清位置。确认前不判断是否经过、不规划新路线，也不列收费站方案。涉及“这条路线”的核查时，仅以客服在本会话已生成并展示的具体路线为对象；确认后若尚无路线，先生成并展示一条真实默认路线，再核查它。直接要求经指定地点规划时，无须先生成默认路线。
2. 每轮区分四种意图：核查当前路线是否经过某地、查询给定起终点下有无经过某地的路线、规划必须经过某地的新路线、查询可经哪些收费站的路线方案。地点身份不明确时先澄清。
3. 核查当前路线时，只检查第 1 步确定的具体路线；能验证则回答“这条路线经过／不经过 XX”，不能用“存在另一条经过 XX 的路线”代替。已有有效客服路线且乘客未提出改线时，本轮以结论结束，不生成新路线卡片，也不改变当前路线；第 1 步才新生成的默认路线须在本轮展示。
4. 查询是否存在经过路线时，只对本次起终点及查询条件给出“找到可验证路线／未找到可验证路线／暂无法确认”等结论，不将其表述成当前路线的事实。问答后保持对话可继续。
5. 乘客明确要求经过指定地点的新路线时，确认具体地点及乘客明确提出的“进入／从收费站上高速或下高速”等要求；验证真实路线确实经过或到达该地点。若多个地图地点都可能对应名称，先让乘客确认地点身份。验证成功后直接返回一张新路线卡片和这条路线的预计行驶时间，不要求乘客再从已算出的路径中完成一次形式上的选择。
6. 乘客问“从 A 到 B 可以经过哪几个收费站到达”时，查询可验证的不同收费站路线方案，展示各方案的收费站和预计行驶时间，标明地图默认方案。乘客在有效期内选定一个方案后，核对其仍符合本轮起终点和明确的通行要求，再返回该方案的完整路线卡片及预计时间；不得把未经验证的 POI 名单当作路线方案。
7. 乘客继续追问或修改条件时沿用仍有效的信息；地图服务缓存失效时先在同一对话框重新确认起终点，确认消息照常持久化，随后重新查询或规划，不用旧路线核查。起终点或途经地点变化使受影响的旧核查结果和方案失效。地图服务失败、证据不足或不可达时明确说明，不编造卡片或预计时间。

#### 产品基准案例：德清到西溪湿地

以下是用户提出的完整业务情境，用于后续设计、实现和验收对照。三墩、五常的实际可达性、地图默认路线及耗时在本例中均为情境假设，不能作为地图事实写死；真实回答须由本轮地图数据验证。

**路径一：已有路线，先核查，再由乘客决定是否改线。**

1. 乘客打开 AI 客服，问“帮我规划一条从德清高速路口到西溪湿地的路线”。客服从本次对话识别两端，先问“起点是德清高速路口，终点是西溪湿地，对吗？”必要时附上具体城市或地址。乘客确认后，客服才用地图生成并展示一条真实默认路线，将其作为本会话当前讨论路线。在本例假设的地图结果下，该路线经三墩高速路口下高速；地图页此前是否已有路线，不影响客服本次的规划结果。
2. 乘客认为三墩高速路口可能拥堵，希望改走五常高速路口，于是先问：“这条路线经过五常高速路口吗？”客服核查的是第 1 步那条具体路线。在本例假设的地图结果下，回答“当前这条经三墩的路线不经过五常高速路口”。若实际核查结果为经过，就回答“经过”。乘客得到答案后可以停止提问；客服不主动改线，也不把乘客的拥堵判断当作已证实的实时路况。
3. 乘客继续在同一对话中说：“帮我规划经过五常高速路口的路线。”客服沿用已确认的起终点，确认具体收费站，使用地图规划并验证一条确实经过五常的可行路线。成功后直接返回这条新路线的完整卡片，并说明：“这条路线预计行驶 X 分钟。”X 来自本次地图路线；无需计算它比原来经三墩的路线多花几分钟。无法验证时不编造路线或预计时间。

**路径二：乘客一开始就询问可选收费站路线。**

1. 乘客打开 AI 客服问：“从德清到西溪湿地可以经过哪几个收费站到达？”客服先复述起点和终点，必要时澄清“德清”的具体出发地点；乘客确认后，才查询并验证路线方案。在本例假设的结果下，展示“经三墩高速路口（地图默认方案）”和“经五常高速路口”等可选方案，标出各方案的预计时间和收费站通行角色。这些是有实际路线支撑的方案，不是收费站地点搜索结果，也不承诺列出全部可能路线。
2. 乘客选中一个仍有效的方案，例如经五常高速路口。客服核对选择与本轮条件一致后，返回该方案的完整路线卡片，并说明这条路线预计行驶 X 分钟。若地图只验证出一个方案，就只展示一个；乘客也可以继续提问或改变要求。

**路径三：乘客首轮已确认两端并直接提出路线需求。**

1. 乘客说：“我确认从德清高速路口到西溪湿地，必须经过五常高速路口，帮我规划。”若地图唯一确定三处地点，客服本轮直接规划并验证经过五常的路线，成功后返回路线卡片与“这条路线预计行驶 X 分钟”；不先生成经三墩的默认路线，也不再追问“起终点对吗”。若五常或两端的地点身份有歧义，先澄清具体地点；无法验证实际经过时不生成成功卡片。
2. 若首轮改问“我确认从德清高速路口到西溪湿地，这条路线经过五常高速路口吗？”，客服内尚无路线时，本轮先生成并展示真实默认路线，再核查这条路线，回答经过、不经过或暂无法确认；不自动改线。若问的是“我确认从德清高速路口到西溪湿地，有没有经过五常高速路口的路线？”，则只回答本次是否找到可验证的经过路线，不把它说成默认路线的事实，也不强制返回路线卡片。

后续评审以这三条路径为产品基线：客服会话从零确认起终点并建立自己的路线；首条消息已明确确认且地点可唯一确定时可以直接处理；是否经过的问题可独立结束；指定五常后验证成功应直接得到新路线卡片和自身预计时间；只有乘客主动询问可选收费站路线时才需要先展示方案并等待选择。本期到卡片和说明为止，不判断乘客是否真的出行，也不要求计算新旧路线的差值或用旧路线方向否决新路线。任何新方案若改变这些边界，应先指出与本案例的冲突，再由产品评审决定是否调整。

### 5.3 地点澄清与路线方案选择

- 起点或终点名称对应多个真实地图地点时，先用名称、城市和地址追问乘客所指位置；明确具体位置后仍须复述完整起终点，等待乘客确认。这一步不等于指定途经点身份澄清或收费站路线方案选择。
- 地点候选用于澄清“乘客所说的 XX 究竟是哪一个地点”；路线方案用于回答“从 A 到 B 可以经哪些收费站到达”。两种候选的含义、有效期和后续动作均应清楚标注，不能把原始 POI 列表冒充已算好的路线方案。
- 多个可能地点时，在对话中展示乘客可理解的名称、地点类型、城市或地址；不要直接展示原始高德 JSON、坐标或让乘客猜测道路哪一侧。
- 乘客选择地点后，服务端按当前对话、当前请求和候选有效期核对选择；过期或条件已改变时重新查询。候选选择的具体有效时长在技术评审中确定，不能复用过期地点数据直接规划。
- 地点选择只确定乘客指向的地点，不证明路线已实际到达或经过它。系统随后验证路线；仅从附近道路擦过、入口不可达或乘客明确要求进入却未到达站点时，不得返回成功规划。不把与旧路线方向相反、合法掉头或绕行本身作为失败原因。
- 只有一个地点也须完成同样的路线验证，但不增加一次形式上的乘客选择。
- 开放式收费站路线查询需从实际可行的地图路线中整理不同收费站方案。每项至少标明所经收费站、预计时间、是否为地图默认方案，且有可核查的路线依据；不能承诺列尽所有可能收费站。展示数量、去重和排序规则由技术方案确定。
- 乘客选择路线方案时，服务端核对该方案属于本次会话、本次起终点与偏好，且尚在有效期内。成功后展示所选方案的完整路线卡片；方案过期或条件变化则重新规划。开放式查询中的选择是乘客明确要求的交互，与指定五常收费站后无需再选择路线并不冲突。
- 指定某个地点重新规划而地图返回多条符合条件的路径时，系统按待评审的推荐规则选一条展示；不得让模型凭空挑选，也不得强制增加选择步骤。乘客可继续追问其他可行方案。

### 5.4 路线规划卡片与回答

| 内容 | 展示要求 |
| --- | --- |
| 起终点与途经点 | 与本轮确认的起终点、乘客选定或唯一明确的地点一致 |
| 路线地图 | 展示真实返回的路线折线、起终点及途经标记 |
| 条件结果 | 成功卡片只展示已验证满足的途经要求；不满足或无法验证时以文字说明，不生成成功卡片 |
| 总里程与预计行驶时间 | 来自地图结果，单位明确 |
| 生成时间 | 帮助用户理解结果时效 |
| 途经地点标注 | 展示服务端验证为实际经过或到达的具体地点；乘客明确要求进入或从某站上、下高速时，说明已验证的通过方式 |
| AI 生成标识与消息操作 | 消息标注“内容由 AI 生成”，提供复制、重新生成操作 |
| 操作 | 查看路线详情、修改条件、重新规划；已选定开放式查询中的路线方案后不要求再选一次 |

仅在确认进入服务区或加油站的路线后，才可使用“途经 XX 服务区／加油站”的肯定描述。路线预计时间默认不包含用户未指定的休息或加油停留时间，应在有停留意图时提示。

首期路线预览建议使用“地图推荐路线”“预计”等表述，不承诺全局最优，也不把乘客对拥堵的猜测表述为已验证路况。交付路线卡片和预计时间即完成本期功能，不跟踪乘客后续行动。

样式参考（高德 AI 问答，见 5.5）：规划成功时将地图卡片内嵌于对话流，圆角卡片展示路线折线与起终点标记，底部信息条为“地点 · 里程 · 时长”；对话正文按“结论先行 → 途经点 → 本路线预计时间 → 主要道路说明”组织。单纯询问是否经过时无需展示新卡片；开放式收费站查询则先展示可选方案，再在选定后展示完整卡片。新旧路线差值、ETA 绝对到达时刻均不是 P0 必填内容。

### 5.5 界面样式参考（高德地图）

定版评审时以两张高德地图截图作为样式参考（2026-09-13）：

- AI 问答页：结论先行（如“会经过 2 个高速路口”）→ 收费站列表带（入口）/（出口）角色标注 → 里程、时长、高速费汇总行 → 主要道路说明 → 内嵌地图卡片与终点 ETA。
- 首页：宫格“打车”入口、常用出行卡片、底部语音 AI 入口，支撑 5.1 的入口形态。

两点不能照搬的差异：

1. “当前路线是否经过”是具体路线核对，“有没有经过的路线”是可达性询问，“帮我规划必须经过的路线”是带硬性约束的规划，“可以经过哪些收费站”是可选路线方案查询；四者可在同一对话中连续发生。
2. 新路线只需说明其自身预计行驶时间；第 6.5 节只管理当前路线的核查对象与结果时效，不要求计算新旧路线差值。

## 6. 路线业务规则

### 6.1 “经过”的语义

- 任何路线问答都先明确起点和终点。乘客问“当前路线经过 XX 吗”时，回答针对当前已确认的具体路线及其地图证据；问“从 A 到 B 有没有经过 XX 的路线”时，回答针对本次给定起终点和地点的查询。缺少核查对象时先确认，不能仅凭起终点或地名回答“经过”或“没有经过”。
- “当前路线不经过”只能用于已经核对的当前路线；“在当前查询条件下未找到可验证的经过路线”不等于断言所有道路都不存在这样的路线。外部查询失败或证据不足时回答“暂无法确认”。
- 规划意图中的“必须经过”是硬性条件；成功回答必须附上满足该条件的真实规划路线和依据。先前询问阶段得到的结论不自动成为规划成功结论。收费站路线方案查询的每个可选项也必须对应已验证路线，不能只按收费站名称推测可达。

| 地点类型 | 规则 |
| --- | --- |
| 收费站 | 未指明通行角色时，只验证路线实际经过可信收费站导航点或收费通道；明确要求从该站上高速、下高速时再核对对应角色 |
| 服务区 | 只说“经过”时，以路线实际到达该站可通行导航点为准；说“进去休息”时核对可通行入口，不以从附近主路擦过替代 |
| 加油站 | “去加油”“到加油站”等表达视为到达站点；不能把附近主路视为已到达 |

地点选择不等于路线验证或经营状态确认。没有可靠营业信息时，不承诺加油站营业、油品有货或服务区设施可用。

### 6.2 地点与实际经过

- 地点标识、坐标和入口信息须来自可信地图服务或经核实的业务数据。
- 同名不同城市或不同地址属于地点身份歧义，应展示可理解的地点候选让乘客确认；同名服务区不同道路侧可作为不同地图地点评估，但不以相对旧路线的方向筛掉合法的新路线。
- 乘客明确提出从收费站上高速、下高速或进入服务区、加油站时，这些要求必须成为本轮路线验证条件，不能只留在 AI 的回答文字中。
- 用户明确指定偏离普通路线的地点时，只要地图返回合法可行且确实经过或到达该地点的路线，就可以展示其预计行驶时间；不因与原路线方向相反、合法掉头、折返或绕行较远而直接拒绝。
- 无法确认路线是否到达指定地点，或无法满足乘客明确提出的进入、上高速、下高速要求时，结果为“无法验证”，不能标记满足。

### 6.3 硬性条件与冲突

- 规划轮次中用户明确指定的途经地点和通过方式属于硬性条件，不能为缩短路线而自动删除。
- “经过某高速收费站”与“不走高速”等要求发生冲突时，应说明冲突并由乘客调整。
- 用户提出超出首期能力的限制时，说明当前支持范围，不能假装已应用该限制。
- 替代地点或无途经点路线只能作为明确标注的备选，不能替代原要求展示为成功结果。

### 6.4 满足条件的证据

- 需要真实地图算路结果以及指定地点的可信可通行导航点共同支撑。
- 服务区和高速加油站在乘客要求进入或到达时，应验证路线实际到达站点可通行入口；若地图提供完整入口、出口导航点，则可核对经过顺序。收费站应验证路线实际经过可信的收费站导航点或收费通道；用户明确要求上高速或下高速时，再验证相应角色。
- 不能仅以路线折线接近地点中心坐标作为成功依据。
- 路线事实、地点身份和乘客明确表达的通过要求必须逐项对应；仅证明地点附近可达，不等于已经证明“进入服务区”或“从指定收费站上高速”。不另设“新路线必须与原路线同向”的条件。
- 技术方案需说明各类型的可验证范围；缺少足够信息的类型不得以“已验证”上线。
- 本期的“满足要求”只指规划路线本身经过或到达指定地点，不涉及乘客后来是否出行。

### 6.5 当前路线与结果时效

- 乘客问“这条路线是否经过”时，核查对象是本客服会话已生成并展示的具体路线；地图服务短时保留其起终点、路线折线、导航步骤和生成时间。若本会话只有已确认的起终点而没有具体路线，先生成并展示真实默认路线，再核查它。
- 指定地点的新路线只须在已确认的起终点之间满足途经要求，并给出自身预计时间；即使已有旧路线，也不需要计算两条路线的差值。
- 开放式收费站查询如有当前路线，可标明它对应的方案；若没有，可按相同起终点生成地图默认路线作为方案之一。默认路线本身可能经过不止一个收费站，方案名称应突出能够区分路线的收费站，不能将收费站名误写为路线唯一通行点。
- 修改起点、终点、途经地点或乘客明确提出的通行要求后，受影响的旧地点候选和旧规划结果立即失效；按新条件重新查询或规划。
- 新旧请求并发返回时，只将最新请求结果作为本轮有效方案，避免旧路线覆盖新要求；客服展示的新卡片更新本会话后续核查对象，但不修改地图页路线。
- 地图服务中的完整路线快照有效期暂定 5 分钟；过期后历史保留文字、里程和预计时间，不再展开完整折线或用旧路线继续核查。若乘客继续提出路线需求，客服先提醒重新确认起点和终点，双方确认消息均持久化。地点候选和路线方案的选择也须有有效期；短时上下文失效时同样重新确认，不使用过期选项。

## 7. 费用展示边界

定版结论（D-04）：首期不展示预估车费，仅以里程与时间为核心交付；预估车费作为后续增强项单独评审。

若批准加入预估车费，必须满足：

1. 金额由计价服务基于该规划路线计算，模型不得自行计算或编造。
2. 明确标注“预估”，不能展示为最终账单或保证成交价。
3. 高速费若仅是地图提供的估算，应独立标注其来源及是否包含在车费内；未确定收费口径前不并入订单金额。
4. 无法取得费用时，仍可展示路线，费用显示“暂无法估算”，不填 0 元。
5. 当前结算存在 mock 指标；不能将真实地图的预览估算静默写入既有 mock 结算链路。

示例文案仅作格式参考，数值由业务结果填充：

> 已找到可进入 XX 服务区的路线，预计行驶 X 公里、Y 分钟。预计时间不包含您在服务区的停留时间。

## 8. 异常与降级

| 情况 | 产品行为 |
| --- | --- |
| 起终点任一缺失 | 先引导补充，保留已明确的途经要求；补齐前不回答是否经过、不规划或展示收费站方案 |
| 当前路线或核查对象不明确 | 先问清要核查哪条路线或哪组起终点，不直接回答“经过／没有经过” |
| 只有起终点、没有具体当前路线 | 先用地图生成并展示默认路线，再核查“这条路线”；不能假定乘客正在使用某条路线 |
| 地点查无结果 | 请用户补充名称或区域，不编造地点 |
| 多个可能地点 | 展示可理解的地点候选供乘客在有效期内选择；地点未确定前不返回声称满足要求的规划卡片 |
| 地点选择已过期或条件变化 | 旧选择失效；先重新确认起终点，再查询地点，不拿旧地点或旧路线继续规划 |
| 收费站路线方案过期或条件变化 | 旧方案不可选；先重新确认起终点，再按新条件查询，不返回失效方案的路线卡片 |
| 开放式收费站查询只验证到一个方案 | 如实展示一个并说明是本次找到的方案，不虚构第二条、不声称穷尽所有道路 |
| 指定地点身份或实际经过无法验证 | 说明缺少的地点或地图导航证据；不把附近擦过的路线说成已到达站点，不因与旧路线方向相反而直接拒绝 |
| 地点可查询但无法算路 | 说明暂未找到可达路线，允许更换地点 |
| 路线无法验证途经条件 | 标记无法验证，不作为满足条件的推荐路线 |
| 是否经过的查询未找到结果 | 区分“当前路线不经过”与“当前条件下未找到可验证路线”，不声称所有路线都不存在 |
| 用户条件冲突 | 说明冲突，等待调整后重新规划 |
| 地图或模型超时、限流 | 明确失败状态，支持重试；不无限循环调用 |
| 模型解析出错或输出无效 | 不触发不合法工具调用；允许用户重新描述或补充地点信息 |
| 地图展示失败 | 提示地图加载失败，保留可核实的路线摘要与重试入口 |
| 计价失败 | 路线可继续展示，费用标记不可用 |
| 登录失效 | 引导重新登录，不泄露其他用户的会话内容 |
| 用户修改条件或取消 | 旧请求不得覆盖当前结果；停止不必要的后续处理 |

关闭 AI 功能或其依赖不可用时，既有普通叫车入口仍应可用。

## 9. 非功能要求与验收指标

时间类指标已随 D-07 定版；模型与地图调用次数、用户频率等外部调用预算，需结合地图配额、模型及测试环境在技术评审中确定具体数值。

| 维度 | 要求 |
| --- | --- |
| 反馈速度 | 提交后 1 秒内显示受理或处理中状态 |
| 完整响应 | 信息完整、外部服务正常的请求，端到端 P95 不超过 15 秒；单轮执行超过 60 秒时结束并支持重试 |
| 调用控制 | 设置模型调用次数、地图调用次数、总执行时间及用户频率上限，具体数值在技术评审确定 |
| 数据依据 | 验收样本中的地点、路线和数值均可追溯，不得出现虚构地点或数值 |
| 条件遵守 | 验收样本中不允许静默丢弃硬性途经条件 |
| 核查准确性 | 起终点明确后，“当前路线是否经过”的结论只能依据本轮确定的具体路线；不能用另一条可达路线替代 |
| 方案依据 | 展示的每个收费站路线方案均有对应的有效地图路线与途经验证，不用 POI 名单或模型推测充数 |
| 交付边界 | 新路线卡片仅需准确展示该路线预计时间；不计算新旧路线差值，不跟踪乘客后续行动 |
| 隔离 | 用户身份由认证上下文确定；客户端传入会话标识不能访问其他用户数据 |
| 信息最小化 | 仅提供路线任务必要的位置和文本信息给模型，不附带手机号、支付信息或无关历史订单 |
| 指令边界 | 用户输入、POI 文本不能改变服务端权限或开放未授权业务工具 |
| 可观测性 | 可追踪请求、地点消歧、地图调用、校验状态、耗时和错误原因；日志避免记录密钥与完整敏感位置历史 |
| 发布控制 | 支持按环境或用户范围启用，能够关闭该功能并恢复普通出行入口 |

验证成功率需单独统计“符合能力范围且信息完整的请求”；缺少信息、无真实可达路线与服务故障分开统计，不用模糊的总成功率掩盖问题。

## 10. 若首期接入下单，必须补充的范围

D-01 已决议：首期不接入下单，本节范围整体后移至下一阶段评审，不计入本次定版实施：

- 用户主动选择路线并确认下单，客服不能自行发起订单。
- 下单前重新验证路线有效性及报价变化，并展示发生变化的内容。
- 保存可追溯的已选路线、途经要求、计价输入及数据来源；是否建表由技术方案评审决定。
- 乘客订单详情和司机端展示一致的途经要求，派单、改派后不能丢失。
- 定义司机是否接受停靠、允许停留时长、额外费用及无法执行时的处理方式。
- 与现有订单幂等、状态机、取消和结算快照规则兼容。
- 明确从 mock 地图及计费指标向真实数据过渡的范围，不改变历史订单的冻结口径。

## 11. 验收用例

所有成功用例使用可核实的地图数据；mock 用于异常和边界测试时必须标识，不能证明真实道路可达。

| 编号 | 输入或条件 | 预期结果 |

| AC-01 | 乘客在客服里说明 A、B 和唯一收费站并要求规划，但未明确确认两端 | 先复述起终点并等待明确确认；确认后验证路线实际经过该站，返回一张路线卡片和该路线预计时间 |

| AC-03 | 存在不同城市的同名地点 | 在对话中展示城市、地址等可区分的地点候选，乘客选定地点后再规划，不静默猜测 |

| AC-05 | 用户要求进入加油站，路线仅从附近主路通过 | 不能判定为满足 |

| AC-11 | 已生成路线后修改终点或途经点 | 修改终点时旧路线失效，客服复述更新后的完整起终点并等待确认；修改途经点时旧方案失效，按已确认起终点重新规划 |
| AC-12 | 上一次请求晚于新请求返回 | 旧结果不覆盖新条件和新结果 |
| AC-13 | 当前旧路线不可用，但乘客已给出明确起终点和指定地点并要求新路线 | 可独立规划新的途经路线，成功后只说明新路线预计时间，不依赖旧路线做差值计算 |
| AC-14 | 结果超过有效期 | 提示重新规划，不继续标为最新结果 |
| AC-15 | 模型或地图超时、限流 | 有明确失败及重试入口，无无限等待 |
| AC-16 | 用户取消规划 | 不继续展示为成功，不修改或创建订单 |
| AC-17 | 用户伪造其他会话标识 | 无法读取或覆盖其他用户信息 |
| AC-18 | 用户或 POI 文本要求绕过权限、忽略业务约束 | 不执行越权工具或丢弃途经要求 |
| AC-19 | 关闭功能开关 | 普通叫车流程仍可使用 |
| AC-20 | 预估车费增强项获批后计价失败 | 路线仍可展示，费用明确不可用 |

| AC-22 | 乘客问“从 A 到 B 有没有经过 XX 的路线” | 查询后简洁回答是否找到可验证路线；查询失败或证据不足时说明暂无法确认，不断言所有路线都不存在 |
| AC-23 | 当前经三墩的路线不经过五常；乘客随后在同一对话要求“帮我规划经过五常” | 沿用明确的起终点，验证可行后返回经过五常的新路线卡片和该路线预计时间；不要求计算相对经三墩路线的差值 |
| AC-24 | 规划时仅有一个明确地点 | 不要求乘客完成形式上的选择；验证成功后直接返回一张路线卡片 |
| AC-25 | 规划时找到多个可能地点 | 展示地点候选，乘客在有效期内选定一个；服务端核对选择与当前条件后再验证和规划，返回一张路线卡片 |
| AC-26 | 地点候选过期、乘客更改条件或路线是否实际经过所选地点无法验证 | 不使用旧地点继续规划，不返回声称满足要求的卡片；重新查询或说明无法验证 |
| AC-27 | 指定五常收费站后地图返回多条合法路径 | 按明确的服务端推荐规则展示一条经验证的规划路线，不要求乘客再完成一次形式上的路线选择 |
| AC-28 | 客服先收到“从 A 到 B 规划路线”，随后乘客问“这条路线经过 XX 吗” | 客服先复述 A、B；乘客确认后生成并展示具体地图默认路线，后续才以该路线为核查对象；只凭 A、B 文本不得回答当前路线经过与否 |
| AC-29 | 乘客问“从德清到西溪湿地可以经过哪几个收费站到达” | 先确认具体起终点，乘客明确认可后才基于实际地图结果展示已验证的收费站方案，标注默认方案和预计时间；不把收费站 POI 名单当作路线方案 |
| AC-30 | 开放式查询展示经三墩和经五常两个有效方案，乘客选择经五常 | 核对该方案所属会话、起终点与有效期后，返回经五常的完整路线卡片和自身预计时间 |
| AC-31 | 收费站方案只找到一个、选择已过期或乘客修改起终点 | 只展示真实找到的方案；过期或条件变化后不得返回旧方案卡片，应先重新确认起终点，再查询或说明暂不可用 |
| AC-32 | 新路线与旧路线生成时间或导航偏好不同 | 仍只展示新路线自身的地图预计时间，不计算或宣称新旧路线差值 |
| AC-33 | 乘客要求经过接人地点等本期范围外的任意地点 | 告知目前仅支持收费站、服务区和加油站，不假装已按接人地点规划 |
| AC-34 | 当前路线经核查确实经过乘客指定的收费站，乘客未继续提出规划要求 | 回答“这条路线经过该站”并结束本轮问答；对话保持开放，不自动生成新路线或要求选择方案 |
| AC-35 | 乘客未说明起点或终点，却询问“经过五常吗”或“有哪些收费站可走” | 先补齐起终点，再确定核查对象或规划方案；不凭地名推测回答 |
| AC-36 | 地图给出合法且实际到达指定地点的新路线，但路线与原路线方向相反或发生合法掉头、绕行 | 不以相对原路线的方向、掉头或绕行本身否决；按该路线是否实际到达指定地点判断，并只说明其预计时间 |
| AC-37 | 地图页已选 A、B 或已有路线，乘客首次进入客服只说“这条路线经过五常吗” | 客服不读取地图页条件；先追问并复述起终点，等待乘客确认，再生成并展示本会话默认路线后核查 |
| AC-38 | 客服路线完整快照过期，乘客查看历史或继续问“这条路线” | 历史显示文字、里程和预计时间，不展开旧折线；客服先询问并等待乘客重新确认起终点，旧路线有指定途经点时再确认是否仍需经过该点；将双方确认消息保存在原会话，之后才按新条件生成并展示路线进行核查 |
| AC-39 | 本会话首次识别到完整起终点，但乘客在消息中未明确确认，且尚未回复确认或回复“不对” | 客服只复述并等待修正或确认；不得提前调用驾车算路、输出经过结论、路线卡片或收费站方案 |
| AC-40 | 乘客确认起终点后，在地图服务临时上下文仍有效时继续问经过或改线 | 沿用已确认的两端，不逐轮重复确认；乘客更改任一端或缓存失效时使旧路线失效并重新确认两端 |
| AC-41 | 起点或终点名称匹配多个地图地点 | 先以城市、地址等信息澄清具体位置，再复述完整起终点等待确认；不静默采用地图返回的第一条 |
| AC-42 | 首条消息明确确认 A、B，要求必须经过唯一明确的 XX 收费站；地图可唯一确定三处地点 | 同一轮直接规划并验证经过 XX，返回一张路线卡片和该路线预计时间；不生成默认路线、不重复询问“对吗”、不要求再次选择路线 |
| AC-43 | 首条消息明确确认 A、B，问“这条路线经过 XX 吗”；客服会话尚无路线，地图可唯一确定地点 | 同一轮生成并展示真实默认路线，核查该路线是否经过 XX；不自动生成经 XX 的新路线。若改问“有没有经过 XX 的路线”，只回答本次查询结论 |
| AC-44 | 首条消息明确确认 A、B，但起点、终点或指定地点对应多个地图地点 | 先澄清具体地点，不凭“我确认”跳过地点身份核对或静默选地图首条结果 |
| AC-45 | 路线或地点选项缓存失效后，客服要求重新确认起终点，乘客回复“对”或修正地点 | 客服提问、乘客回复及后续结果都按顺序进入同一会话历史；重新查询地图地点并核对身份，不能把旧文本或旧 `routeRef` 当作有效地图事实 |

发布前须补齐各支持地点类型的真实成功案例、地点身份歧义案例和不可达案例，并记录验证证据。AC-20 仅在费用增强项纳入首期时适用。

## 12. 当前项目基础与开发约束

### 12.1 当前基础

- 地图路线请求已支持按顺序传入多个导航点；服务区和高速加油站使用入口、出口两个有序点。

- 现有完单结算 PRD 采用本地 mock 规划距离与 mock 计费时长，本 PRD 不直接覆盖其规则。
- 依赖升级已完成（2026-09-13 用户确认）：根 POM 为 Spring Boot 3.5.16、Spring Cloud 2025.0.3、Spring Cloud Alibaba 2025.0.0.0，并引入 Spring AI 1.1.2、Spring AI Alibaba 1.1.2.0、extensions 1.1.2.1 三个 BOM；各微服务子模块 nacos starter 已移除硬编码版本随 BOM 对齐；gateway 不再固定 4.1.5。
- map 模块已同时保留 `spring-ai-alibaba-starter-dashscope` 和引入 DeepSeek 专用的 `spring-ai-starter-model-deepseek`；当前路线 Agent 计划通过 DeepSeek 专用 starter 和 `DEEPSEEK_API_KEY` 直连 DeepSeek，DashScope starter 作为可选百炼接入方式保留，两个 Key 均只通过环境变量注入。
- 现有 Spring AI Tool 仅接受地点关键词、可选地区和地点类型；具体当前路线、乘客明确表达的进入或上、下高速要求，以及在对话中修改起终点的条件尚未贯通到核查和规划验证。开放式收费站路线方案的发现、验证与选择契约也未实现。模型不能自行补造坐标、地点或路线。
- 仓库存在长期会话三表 SQL；此前文档记载该脚本已执行，本次未核对实际数据库结构。该脚本与 TECH、API、TEST 仍采用旧的路线候选选择契约，不能直接作为本版产品流程的实施依据。Agent 对话服务、乘客 BFF 接口和前端真实数据联调仍待实施。

### 12.2 服务职责约束

- Agent 负责理解、必要追问、调用业务工具和解释结果。
- 地图服务负责地点查询、算路与路线事实；具体校验职责在技术方案中落实。
- 计价服务负责金额计算；订单服务负责订单状态与冻结快照。
- 乘客请求经过现有网关及乘客端 BFF 的认证边界。
- PRD 不预设新增数据库表、服务模块、接口路径或 Java 类名，这些分别评审。

### 12.3 逐步实施方式

实施顺序：本版产品主流程评审 → 对齐 PRD、TECH 和 API 中的客服独立路线来源 → 核对已有代码和实际数据库结构 → 按批次实现地图服务短时路线快照、客服会话核查、指定途经点改线、开放式收费站方案查询与选择 → 乘客 BFF 与前端真实交互 → 最后更新 TEST 并做真实地图场景验收。旧的 `routeCandidateId` 选择契约不能直接用于全部意图；尤其不能将每次指定地点规划都变成强制路线选择。

本次同步修订 PRD、TECH 和 API 的地图页与客服隔离契约；TEST、SQL 和未提交代码中仍有旧流程，不得将它们视为已经完成的端到端实现。

每次实施前列出要新增或修改的文件、目的、范围和验证方法；用户同意后仅执行该批次。出现必须扩大范围的兼容问题时，先报告原因及具体变更，再取得同意。服务启动、停止和重启仍由用户明确授权。

## 13. 评审决议记录（2026-09-13、2026-09-17）

| 编号 | 决策事项 | 决议 |
| --- | --- | --- |
| D-01 | 首期做路线预览，还是必须贯通下单与司机展示？ | 只做路线预览；贯通下单与司机展示另列下一阶段（第 10 节整体后移） |
| D-02 | 首期途经点数量？ | 单个指定地点；用户提出多个时引导先选一个 |
| D-03 | 是否批准接入真实地图地点查询与算路？ | 批准接入高德真实 API，先做最小能力验证（POI 搜索、途经点算路、折线解析）；实际接口调用和配置按批次实施 |
| D-04 | 首期是否展示预估车费？ | 首期不展示，仅里程与时间；费用作为后续增强项单独评审 |
| D-05 | 服务区或加油站只说“经过”时如何处理？ | 原决议是路过与进入有歧义时追问；按 D-18 简化为验证路线实际到达该站的可通行导航点，乘客明确要求进站时再核对入口。地点身份不清或地图证据不足时才追问，不为比较道路方向而追问 |
| D-06 | 入口与结果有效期？ | 叫车页起终点区域入口；有效期暂定 5 分钟 |
| D-07 | 性能目标及外部调用预算？ | 2026-09-13 原定 1 秒受理、P95 不超过 15 秒、30 秒强制截止；2026-09-16 用户确认将单轮执行上限调整为 60 秒，其余两项不变。模型/地图调用次数与用户频率上限在技术评审确定 |
| D-08 | 乘客只询问是否经过指定地点时，是否必须规划并选择路线？ | 2026-09-17 用户明确：先回答核查结论，该轮问答从乘客目的看已结束；对话框仍开放，可继续提出规划需求 |
| D-09 | 规划时出现多个同名或近似地点，由谁选择什么？ | 2026-09-17 用户明确：在对话中展示多个地点候选，乘客在有效期内选择具体地点；后端随后验证和规划。地点澄清与 D-13 的路线方案选择是不同交互 |
| D-10 | 已指定途经地点后，规划轮次的最终交付是什么？ | 最初要求返回路线卡片及相对当前路线的时间差；后续按 D-16 修订为只返回路线卡片和该路线自身预计时间，此分支不要求再完成一次形式上的路线选择 |
| D-11 | “当前路线”指什么？ | 2026-09-17 用户明确：核查必须针对一条具体地图路线；按 D-19 修订后，仅指客服会话内生成并展示的路线，只有起终点而无路线时先在客服内建立默认路线 |
| D-12 | 当前路线不经过乘客想去的地点时如何处理？ | 先如实回答“不经过”，不自动改线；乘客继续要求经过该地时，再验证新路线并返回路线卡片及自身预计时间 |
| D-13 | 乘客询问“可以经过哪几个收费站到达”时如何处理？ | 先展示本轮地图已验证的不同收费站路线方案及默认方案；乘客选定一个有效方案后，再返回完整路线卡片和时间说明。此处的路线方案选择是用户明确需求 |
| D-14 | P0 地点范围是否包含接人地点等任意具名地点？ | 用户确认先做收费站、服务区、加油站三类；接人等其他地点后续评审 |
| D-15 | 能否在起点或终点不明确时回答经过地点或规划路线？ | 用户明确不能：先明确起点和终点，再核查具体路线、规划途经路线或列收费站方案 |
| D-16 | 新路线是否必须计算相对旧路线多花的时间？ | 用户明确不必：成功卡片只说明新路线自身预计行驶时间，不计算新旧路线时间或里程差 |
| D-17 | AI 客服交付范围是否包含乘客后续行动？ | 用户明确只做到路线卡片和时间说明，不跟踪乘客是否按路线出行、下单或实际到达 |
| D-18 | 是否继续按与原路线的方向、掉头或绕行情况排除新路线？ | 用户明确取消这类附加筛选。只要地图证明新路线合法可行且实际经过或到达指定地点，就可展示；仅在乘客明确要求进入、上高速或下高速时验证对应动作 |
| D-19 | 地图页条件能否带入 AI 客服？ | 用户明确隔离两者。新客服会话从空条件开始，乘客在客服里重新说明起终点；本会话可沿用已确认条件及客服生成的路线，地图页的起终点、路线和导航状态均不传入 |
| D-20 | 客服完整路线快照存在哪里，历史过期后如何展示？ | 用户明确完整路线与导航步骤由 map-service 短时缓存，不放在 passenger-service；过期后历史仅保留文字、里程和预计时间，不再展开完整折线或继续核查旧路线。缓存实现由 TECH 定义 |
| D-21 | 乘客在客服文字里给出起终点后能否立即算路？ | 用户确认：乘客只给出两端、尚未明确确认时，客服先复述并提醒确认；地点有歧义时先澄清。确认前不进行驾车算路、经过判断或收费站方案查询；同一会话可沿用已确认两端，修改任一端须重新确认。首轮已明确确认的例外见 D-22 |
| D-22 | 首条消息已明确确认起终点并提出途经或核查需求，是否还必须再等一条“对”？ | 用户确认直接处理：地图可唯一确定地点时，首轮明确确认即足够，不重复追问。指定地点规划直接验证并出卡；询问“这条路线”而客服尚无路线时先展示默认路线再核查；询问“有没有经过的路线”只作存在性查询。地点有歧义时仍先澄清 |
| D-23 | 客服短时地图缓存失效后如何继续对话？ | 用户确认：客服请乘客重新确认起点和终点；确认提问、乘客回复和后续结果均通过 `passenger-service` 持久化为原会话消息。`passenger-service` 不为路线另存长期权威快照或额外业务状态 |
