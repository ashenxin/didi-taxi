# 车队营销优惠券规则讨论稿

> 本文档用于沉淀当前关于「优惠券/营销计价规则」的讨论结论与待确认口径。
> 本文档为讨论记录，不直接进入代码开发；当前结论已拆分为《车队营销优惠券_PRD.md》《车队营销优惠券_TECH.md》《车队营销优惠券_API.md》《车队营销优惠券_SQL.md》。

## 1. 背景

在「我的钱包：免密支付与优惠券」功能讨论中，优惠券最初被设计为乘客钱包资产，放在 `calculate` 库中，用于调整订单实付金额。

后续讨论发现，优惠券不只是钱包入口展示能力，而是会影响：

- 基础计价后的金额调整
- 乘客最终支付金额
- 司机/车队/平台收入分配
- 退款、发票、对账
- 车队运营活动配置
- banner、广告、活动页等营销投放入口

因此优惠券应被重新定义为：**车队可配置的营销计价规则**。

## 2. 当前用户明确提出的方向

### 2.1 必须支持的优惠券类型

模板表必须直接支持以下常见规则：

| 类型 | 示例 | 是否必须内建支持 |
| --- | --- | --- |
| 固定金额减免 | 满 35 减 5；无门槛减 3 | 是 |
| 比例折扣 | 满 35 打 9 折；全单 8 折 | 是 |
| 封顶折扣 | 打 8 折，最多减 20 元 | 是 |
| 日期/节日/限时类 | 国庆 10 月 1 日到 10 月 7 日；下周五 08:00 到 20:00 | 是，仅支持固定开始/结束时间 |
| 适用范围类 | 仅杭州可用；仅快车可用 | 是，仅支持城市和产品线 |

说明：

- 「封顶折扣」可理解为 `比例折扣 + 最大优惠金额`。
- 日期/节日/限时类本期不做复杂周期规则，例如每周五自动生效、法定节假日自动识别、每日固定时段循环等。
- 如果需要“下周五早 8 点到晚 8 点”，后台直接配置固定 `valid_start_at` 和 `valid_end_at`。

### 2.2 特殊优惠券处理方式

除上述常见类型外，其它类型先归为特殊优惠券。

特殊类型可以通过以下方式预留：

- 配置文件
- Redis 配置
- `coupon_rule` 或 `rule_config` 字段
- 通过发版开启特定活动
- banner、活动图片、广告点击后领取特殊优惠券

用户接受：**不常见活动可以通过运营讨论后再特殊实现，不要求一开始全部后台自助配置化。**

### 2.3 优惠券创建权限

用户当前观点：

- 优惠券归属应下放到车队，即优惠券模板必须明确对应发券车队 `company_id`。
- 车队在不与运营沟通的情况下擅自发布优惠券，容易造成金额、收入分配、经营责任扯皮。
- 优惠券发放应由运营所在公司与车队共同讨论，只有双方都同意，才允许出现正式优惠券。
- 需要充分尊重车队经营权，不存在平台券；运营只能建议某个特殊时刻是否开展活动，不能绕过车队单方面发券。
- 为了降低实现复杂度，同时维护车队与运营所在公司的经营秩序，本期暂定只有唯一超管账号可以在系统里执行发布生成正式优惠券方案。
- 这里的超管发布只是系统执行动作，不代表平台拥有单方面创建平台券或代车队决定活动的权力。
- 车队承担优惠券带来的全部经营责任与优惠成本。
- 特殊优惠券也必须先由运营与车队达成一致，再通过 banner、广告、图片点击等方式获取。

### 2.4 平台服务费口径

已确认：

- 本期平台服务费统一按乘客优惠后实付车费收取 5%。
- 这里不再使用“司机到手金额”作为计算基数。
- 也不按承运侧收入反推计算。

一期口径：

```text
平台服务费 = 乘客优惠后实付车费 * 5%
承运侧收入 = 乘客优惠后实付车费 - 平台服务费
```

司机最终收入、车队收费、司机/车队分账，后续作为独立结算/财务模块讨论。

## 3. 建议确认后的基本原则

### 3.1 优惠券属于营销计价规则（已确认）

优惠券不建议继续只作为钱包功能理解，而应归入 `calculate` 的价格调整能力。

建议定义为：

```text
基础计价 fare_rule
  -> 算出优惠前车费

营销优惠 coupon / promotion_rule
  -> 算出优惠金额、乘客应付金额

结算分配 settlement_rule
  -> 算平台服务费、承运侧收入、司机/车队收入
```

确认该原则后，后续需要按以下方向调整：

- 产品口径：优惠券不再只描述为“我的钱包资产”，而是“车队营销计价规则 + 用户可领取资产”。
- 模块边界：优惠券模板、优惠券校验、优惠金额试算放在 `calculate` 侧；钱包侧只负责展示用户拥有的券和入口。
- 订单链路：下单预估价、选择优惠券、支付前金额确认，都应调用 `calculate` 的优惠计算结果。
- 结算链路：优惠券影响乘客实付金额后，需要继续进入结算分配逻辑，不能只改订单实付金额。
- 数据设计：优惠券模板和使用记录建议继续放在计价库；订单库只保存本单最终金额、优惠金额、优惠券快照或结算快照。
- 文档拆分：后续正式文档建议拆成「优惠券 PRD」「优惠券 TECH/API/SQL」「结算影响补充说明」，避免和钱包免密支付混在一起。

### 3.2 优惠券不要塞进 fare_rule 表（已确认）

虽然用户提出“下放到每个车队自定义的计价规则中”，但建议不要直接把优惠券字段塞进基础 `fare_rule`。

更稳妥的表达是：

```text
优惠券属于车队自定义的营销计价规则，与基础 fare_rule 并列。
```

原因：

- 基础计价规则解决“车费怎么算”。
- 优惠券解决“车费算完后优惠多少”。
- 结算规则解决“优惠后钱怎么分”。

三者混在一张表里会很快膨胀，并且影响历史订单解释。

确认该原则后，后台计价规则页面建议做成“入口联动，数据解耦”：

- 新增或编辑基础计价规则时，提供“是否开启优惠券/营销优惠”开关。
- 开关打开后，不把优惠券字段直接写入 `fare_rule`，而是引导查看或关联该车队的优惠券模板。
- 后台页面上可以把基础计价规则与优惠券配置放在同一条业务流程里，让登录用户理解为“本计价规则下可查看优惠活动”。
- 只有超管账号可以新建、修改、启用、停用优惠券模板；非超管只能查看。
- 数据层仍然拆开：`fare_rule` 只保存基础车费规则；`coupon_template` 或营销规则表保存优惠券模板；两者通过车队、城市、产品线、适用时间等条件共同生效。
- 如果后续确实需要“某张优惠券只绑定某条 fare_rule”，再增加关联表，不建议现在直接在 `fare_rule` 上加大量优惠券字段。

后台交互建议：

```text
计价规则新增/编辑
  基础计价配置
  -> 是否开启优惠券
     -> 否：只保存基础计价规则
     -> 是：保存基础计价规则后，进入优惠券模板查看/超管配置区
```

优惠券查看/配置区建议支持：

- 查看当前车队已配置的优惠券模板。
- 超管新建固定金额减免券。
- 超管新建比例折扣券。
- 超管新建封顶折扣券。
- 超管设置有效开始/结束时间。
- 超管设置城市、产品线适用范围。
- 超管设置总发放量、每人限领量、最低订单金额。

需要注意：这里的“是否开启优惠券”更适合理解为后台流程入口或营销能力开关，而不是 `fare_rule` 表里的强耦合字段。是否需要落库为开关字段，需要后续结合后台页面和权限模型再决定。

最终结论：

- `fare_rule` 不需要新增任何优惠券字段。
- 不需要在 `fare_rule` 上新增“是否开启优惠券”落库字段。
- 后台从某条计价规则详情页进入优惠券方案时，直接用该计价规则的 `company_id + city_code + product_code` 查询同范围下的优惠券模板。
- 优惠券模板自身的 `status` 字段用于表示草稿、已发布、已下架等状态，已经可以满足启用/停用需求。
- 因此，计价规则与优惠券方案保持“维度匹配”，不做 `fare_rule_id` 强绑定。

### 3.3 权力下放给车队，但需要边界（已确认）

历史文档与当前实现确认：

- 《后台管理系统_运力配置_PRD》明确：**一行 `company` 记录 = 公司 + 车队（承运单元）**。
- 同一业务公司可以在同一省市下存在多条 `company` 记录，使用车队名称 `team` 区分。
- `team_id` 是车队业务编码，全库唯一。
- 司机归属字段使用 `driver.company_id`。
- 换队申请使用 `from_company_id` / `to_company_id`。
- 当前计价规则 `fare_rule` 也绑定 `company_id` / `company_no`，业务维度是「公司 + 省 + 市 + 产品线」。

因此，当前系统里的“车队级”不是独立 `fleet` 表，而是 `capacity.company.id` 代表的承运单元。产品上可以叫“车队”，技术落库上建议继续使用 `company_id`，避免引入新的 `fleet_id` 后与现有司机归属、订单归属、计价规则归属冲突。

建议口径：

```text
优惠券创建权限下放到车队级。
这里的车队级，在当前系统中对应 capacity.company.id 这条公司+车队承运单元记录。
后续不再新增 fleet_id，所有车队归属、优惠券适用车队、计价规则承运单元均使用 company_id 表达。
```

我不建议本期为了优惠券再拆一张独立车队表，原因是：

- 现有运力、司机归属、换队、订单派单、计价规则都已经围绕 `company_id` 建模。
- 如果单独新增 `fleet`，需要重构司机归属、车辆归属、计价规则、订单承运方等核心链路，改动面过大。
- 同一业务公司下多车队的诉求，当前已经通过多条 `company` 记录 + `team/team_id` 表达。
- 优惠券本身不应该成为推动运力模型重构的理由。

可接受的增强是：优惠券表主维度保存 `company_id`，同时冗余快照字段用于展示和历史解释：

```text
company_id
company_no
company_name_snapshot
team_id_snapshot
team_name_snapshot
```

其中 `company_id` 用于权限、查询、计算和归属判断；快照字段用于历史订单、优惠券使用记录、后台展示，避免后续公司名或车队名修改后解释不了历史活动。

优惠券归属与使用口径补充：

```text
优惠券模板归属车队 company_id。
乘客领取后，优惠券实例归属于乘客 passenger_id。
乘客可以持有多个车队发放的优惠券。
实际使用时，按最终订单/司机所属 company_id 匹配乘客持有的优惠券。
```

因此，优惠券不是“司机资产”，也不是“订单一开始就强绑定的资产”，而是乘客资产。乘客可以领取所有可领取的优惠券；但在某一笔订单上是否可用，要看该订单最终承运车队、城市、产品线、时间、金额门槛等条件是否匹配。

典型场景：

- 乘客持有 A 车队优惠券，最终派到 A 车队司机：满足其它规则时可用。
- 乘客持有 A 车队优惠券，最终派到 B 车队司机：该券不可用，本单没有该券优惠。
- 乘客同时持有 A/B/C 多个车队的券：支付前按最终 `trip_order.company_id` 过滤，只展示和计算匹配车队的券。
- 如果最终派单车队没有任何匹配的乘客券，则本单无优惠或只能使用不限定车队的特殊券。

这个口径可以解释司机换队问题：司机换队后，其 `driver.company_id` 改变；后续该司机承运订单时，优惠券匹配应以新的 `company_id` 为准。乘客已经领取的旧车队券不会因此自动失效，但只有在订单最终承运车队仍匹配该券时才可使用。

当前司机与计价规则的关联链路：

```text
driver.company_id
  -> 司机所属公司+车队承运单元
  -> 派单选中司机后，order.assign 写入 trip_order.company_id
  -> calculate 按 company_id + province_code + city_code + product_code + 当前时间命中 fare_rule
```

因此，司机不建议直接绑定 `fare_rule_id`。司机绑定的是承运单元；计价规则绑定的是承运单元、城市、产品线和时间段。某个司机最终使用哪条计价规则，应由其所属承运单元和订单上下文共同决定。

需要额外注意当前两段式下单链路：

- passenger-api 下单时会先搜索最近司机，取最近司机的 `companyId` 做预估价。
- order-service 创建订单时会保存 `estimated_amount` 和 `fare_rule_id`。
- 后续异步派单时，capacity 可能再次选择司机，并把该司机的 `companyId` 写入 `trip_order.company_id`。

#### 3.3.1 重点资金风险：异步派单导致预估计价与最终承运车队不一致

> **必须突出：该问题涉及支付金额、优惠券核销、平台服务费、司机/车队收入分配，不能作为普通展示误差处理。**

当前两段式异步派单会带来一个资金口径风险：**预估价命中的 `fare_rule_id` 与最终实际接单司机所属 `company_id` 可能不一致**。

当前 MVP 可接受其作为预估偏差，但优惠券与结算进入后，不能继续把下单预估结果直接用于支付、优惠券核销或收入分配。至少需要在支付前或完单结算前，按最终承运司机的 `company_id` 重新确认价格、优惠券可用性和结算快照。

明确禁止的口径：

- 禁止仅以下单预估阶段的 `fare_rule_id` 作为最终支付计价依据。
- 禁止仅以下单预估阶段的 `company_id` 判断优惠券最终可用。
- 禁止在最终承运司机未确定时，直接核销强车队绑定优惠券。
- 禁止用可能失配的预估金额计算平台服务费、司机收入或车队收入。

阶段性结论：

- 当前代码中，从 `driverId` 到计价规则的链路本身是闭环的：司机归属 `company_id`，计价规则绑定 `company_id`，订单指派后也会写入 `trip_order.company_id`。
- 新发现的问题不在“司机能否关联到计价规则”，而在“两段式异步派单”导致的时序差异。
- 下单预估阶段使用的是当时最近司机的 `companyId`。
- 异步派单阶段最终接单司机可能来自另一个 `companyId`。
- 如果两个车队的计价规则或优惠券模板不同，就可能出现预估价、优惠券可用性、最终结算口径不一致。

建议后续正式方案按以下口径收敛：

```text
预估价：允许基于候选司机 company_id 产生展示用金额。
支付前确认价：必须基于最终承运司机/订单 company_id 重新计算。
优惠券锁定与核销：必须基于支付前确认价和最终 company_id 校验。
完单结算：必须基于最终 company_id、最终金额、优惠券快照和结算快照。
```

若订单在支付前仍未确定最终司机，则不建议提前锁定强车队绑定的优惠券，只能展示“预计可用”或等司机确认后再给出最终可用券列表。

车队自定义优惠券是合理的，但发布权必须收口。本期主要风控不依赖复杂阈值，而依赖超管执行发布：

- 优惠券模板归属车队 `company_id`。
- 车队不能擅自发布正式优惠券。
- 运营所在公司也不能绕过车队单方面发布优惠券。
- 只有运营所在公司与车队双方都同意后，唯一超管账号才能执行发布生成正式优惠券方案。
- 不存在平台券；运营只能提出活动建议，不能作为优惠成本承担主体单方发券。
- 优惠成本与经营责任由发券车队承担。
- 限制最大优惠金额、最低折扣率、同一时间启用数量等硬阈值，本期可以暂不做。
- 每个订单最多使用一张券、优惠后应付金额不能小于 0，仍属于计算安全底线，建议保留。
- 车队只能申请或配置自己范围内可用的券。
- 下架功能可以有，暂定支持。
- 复制模板类提效能力暂时不做。

## 4. 一期建议支持的券模型

### 4.1 固定金额减免

示例：

```text
满 35 减 5
无门槛减 3
```

核心字段：

```text
coupon_type = AMOUNT_OFF
threshold_amount = 35.00
discount_amount = 5.00
```

计算：

```text
if order_amount >= threshold_amount:
    discount_amount = coupon.discount_amount
```

### 4.2 比例折扣

示例：

```text
满 35 打 9 折
全单打 8 折
```

核心字段：

```text
coupon_type = PERCENT_OFF
threshold_amount = 35.00
discount_rate = 0.9000
```

计算：

```text
discount_amount = order_amount * (1 - discount_rate)
```

### 4.3 封顶折扣

示例：

```text
打 8 折，最多减 20 元
```

核心字段：

```text
coupon_type = PERCENT_OFF
discount_rate = 0.8000
max_discount_amount = 20.00
```

计算：

```text
raw_discount = order_amount * (1 - discount_rate)
discount_amount = min(raw_discount, max_discount_amount)
```

### 4.4 日期/节日/限时类

示例：

```text
国庆 10 月 1 日 00:00 到 10 月 7 日 23:59 可用
下周五 08:00 到 20:00 可用
```

核心字段：

```text
valid_start_at
valid_end_at
```

说明：

- 本期只支持固定开始/结束时间。
- 不支持复杂周期，例如每周五长期生效、每天早晚高峰自动循环。
- 如果要做“每周五”，运营每周手动新建固定时间段活动即可。

### 4.5 适用范围类

示例：

```text
仅杭州快车可用
仅上海专车可用
```

核心字段：

```text
city_code
product_code
```

说明：

- 本期只支持城市和产品线。
- 不支持机场、火车站、路线围栏、跨城、指定起终点等更细粒度场景。
- 后续如果要支持，可放入特殊规则配置。

## 8. 当前方案中已经明确的点

以下是当前已较明确、可进入后续文档的点：

1. 优惠券相关表继续放在 `calculate` 库。
2. 优惠券属于营销计价规则，不属于 `wallet`。
3. 模板表必须支持固定金额减免、比例折扣、封顶折扣、固定有效期、城市、产品线。
4. 不存在平台券；优惠券归属车队，发布前由运营所在公司与车队线下沟通清楚，系统内由超管执行发布。
5. 车队可提出配置草稿或申请，但不能自行发布正式可领取、可核销优惠券。
6. 特殊优惠券需要运营与车队共同确认，通过 banner、广告、图片点击或配置活动领取。
7. 特殊规则可以通过 `rule_config`、Redis、配置文件或发版预留。
8. 平台服务费按乘客优惠后实付车费抽 5%。
9. 常规券登录弹框领取，券归属用户 ID，不归属手机号。
10. 每单最多使用一张券，自动选择最优，用户可选择不用券，不做券叠加。

## 9. 需要继续补齐的口径

以下问题需要逐条讨论确认。

### 9.1 车队/公司归属口径

已确认：

- 系统里优惠券归属使用 `company_id`，不再引入更细的 `fleet_id`。
- 本期及后续都用 `company_id` 表示车队承运单元。
- 司机换队不会改变乘客已领取优惠券的归属，优惠券仍属于乘客。
- 司机换队后，订单使用优惠券时以司机新的 `company_id` 作为最终承运车队判断。
- 如果乘客下单后最终匹配到非发券车队，该车队券不可用。

一期口径：

```text
company_id 表示发券车队。
车队券只适用于该 company_id 承运的订单。
乘客可持有多个车队券，但订单只能使用与最终承运 company_id 匹配的券。
```

### 9.2 车队配置权限

已确认：

- 车队不能在不与运营沟通的情况下擅自发布优惠券。
- 运营所在公司也不能绕过车队单方面发布优惠券。
- 优惠券的发放必须由运营所在公司与车队共同讨论，双方都同意后才可以发布。
- 需要充分尊重车队，不存在平台券。
- 运营只能提出建议，例如某个特殊时刻是否开展活动。
- 优惠券涉及乘客支付金额、车队成本、平台服务费、司机/车队收入分配，必须有审核发布口径。
- 本期为了好做发布优惠券，暂定只有唯一超管账号可以在系统里执行发布生成正式优惠券方案。
- 唯一超管执行发布的前提是运营所在公司与车队已经达成一致。
- 车队侧可以有配置草稿、申请或需求录入，但不能直接让优惠券进入可领取、可使用、可核销状态。
- 限制最大优惠金额、最低折扣率、每个车队同一时间启用数量，本期可以暂不做。
- 下架功能可以有，暂定支持。
- 复制模板类功能暂时不做。

建议状态流：

```text
DRAFT 草稿
  -> PUBLISHED 已发布
  -> OFFLINE 已下架

只有超管账号可以执行 PUBLISHED。
已发布优惠券可以由超管下架。
```

功能边界：

```text
车队归属：优惠券模板仍归属 company_id。
发布前提：运营所在公司与车队双方同意。
发布权限：唯一超管执行发布。
平台券：本期不存在平台券。
责任承担：发券车队承担全部优惠成本与经营责任。
金额/折扣/数量限制：本期暂不做复杂阈值。
下架：暂定支持。
复制模板：本期不做。
```

### 9.3 优惠成本承担方

已确认：

```text
不存在平台券。
运营只能建议某个特殊时刻是否搞活动。
是否发布、发布什么内容，由运营所在公司与车队在线下会议或邮件中沟通清楚。
系统不做发布商讨环节，不记录确认人、确认时间、确认凭证等字段。
优惠成本与经营责任全部由发券车队承担。
```

建议写入一期口径：

```text
一期所有优惠券成本由发券车队承担。
平台不额外承担券成本，也不创建平台补贴券。
运营侧只承担活动建议、协商和系统发布流程，不承担优惠成本。
平台仍按优惠后实付金额抽 5% 服务费。
```

### 9.4 平台 5% 服务费计算基数

已确认：

- 本期平台 5% 服务费按乘客优惠后实付车费计算。
- 不按司机到手金额计算。
- 不按承运侧收入反推计算。
- 取消费、附加费、感谢费、小费等特殊金额，本期暂不纳入讨论，后续如要支持需要单独定义金额科目。

一期口径：

```text
平台服务费 = 乘客实付车费 * 5%
承运侧收入 = 乘客实付车费 - 平台服务费
```

说明：

- 这里的“乘客实付车费”指基础计价金额扣除优惠券后的订单车费金额。
- 优惠券成本由发券车队承担，因此平台服务费自然基于优惠后的实付金额下降。
- 后续仍需单独讨论司机与车队内部分配。

### 9.5 司机收入与车队收入分配

已确认的阶段性口径：

- 承运侧后续肯定还会收费，不应默认承运侧收入全部给司机。
- 用户后续计划：在后台新建页面，由公司/车队查询名下司机以及司机名下所有收入，并按规则收取一定费用。
- 该能力暂时不做，不进入本期优惠券开发范围。
- 本期优惠券只把金额计算到“承运侧收入”，不继续拆司机最终收入、车队抽成、司机净收入。
- 司机/车队分账、车队收费、司机收入查询页面，后续作为独立结算/财务模块讨论。

待后续讨论：

- 车队对司机收费比例或规则如何配置？
- 车队收费是按每单固定比例、固定金额，还是月度/周期结算？
- 后台收入查询页面展示订单维度、司机维度还是月度账单维度？
- 优惠券成本是否影响司机侧收入，还是完全由车队承担后再参与车队内部结算？

建议：

```text
优惠券一期只定义到承运侧收入，不直接定义司机最终收入。
司机/车队分账后续作为结算规则单独讨论。
```

### 9.6 发券方式

已确认：

- 本期采用“用户登录时搜索可领取优惠券 + 弹框询问是否领取”的方式。
- 用户每次登录时，系统搜索该用户当前可领取的所有优惠券。
- 如果存在可领取券，前端弹框询问乘客是否领取所有可领取优惠券。
- 用户确认后，一次性领取所有当前可领取优惠券。
- 优惠券实例必须绑定用户 ID，不绑定手机号。
- 用户更换手机号后，优惠券不能丢失；只要用户 ID 不变，用户已领取的优惠券继续归属于该用户。
- banner 点击领取本期暂不做。
- 正式领取流水本期暂不做，最多记录一条业务日志用于排查。
- 用券、锁券、核销、释放、退款恢复等动作必须留痕。
- 手机号仅可作为展示、通知或搜索辅助条件，不作为优惠券归属主键。

建议口径：

```text
优惠券归属：passenger_id / user_id
手机号：不参与归属判断
领取入口：登录弹框确认领取
领取范围：当前用户可领取的全部优惠券
领取流水：本期不建正式流水表，最多写日志
用券留痕：必须落 `coupon_use_record` 或等价用券记录
banner：本期不做
```

预留字段可以保留，但本期不展开功能：

```text
issue_type = LOGIN_CLAIM
source_type = LOGIN_POPUP
```

后续如果要支持 banner、广告或活动页领取，再扩展：

```text
source_type = BANNER / AD / ACTIVITY / CONFIG
```

### 9.7 领取限制

已确认：

- 每个优惠券模板必须设置总发放上限 `total_count`。
- 同一模板默认每个用户最多领取 1 张，即 `per_user_limit = 1`。
- 当模板已领取数量达到 `total_count` 后，该券视为领完。
- 领完后，该券不再出现在登录领取弹窗里。
- 某用户已经领取过某个模板的券后，该用户再次登录时，弹窗里也不再出现该模板。
- 同一用户不允许重复领取多张相同模板券。

一期口径：

```text
模板有 total_count。
模板有 per_user_limit，默认 1。
登录弹窗只展示“当前用户可领取”的券。
已领完的券不展示。
当前用户已领取过的券不展示。
```

### 9.8 使用限制

已确认：

- 一笔订单最多使用一张优惠券。
- 支持系统自动选择最优券。
- 支持用户手动选择不使用优惠券。
- 后续也不支持多张券叠加。

一期口径：

```text
每单最多用一张券。
系统默认选最优券，用户可选择不用券。
不支持券叠加，后续也不扩展券叠加。
```

设计影响：

- 订单或结算快照中只需要保存一张最终使用券。
- 优惠金额只需要计算一次，不需要处理多券顺序、叠加上限、互斥分组等复杂规则。
- 用户选择“不使用优惠券”时，应明确记录本次订单未使用券，避免系统再次自动套用。

### 9.9 优惠券最优选择规则

已确认：

- 先计算每张券在本单上的实际优惠金额。
- 选择实际优惠金额最大的券。
- 如果优惠金额相同，优先选择更快过期的券。
- 如果优惠金额和过期时间都相同，再按券 ID 更小者优先，作为稳定兜底排序。

一期口径：

```text
先计算每张券在本单上的实际优惠金额。
优惠金额高者优先。
金额相同则 valid_end_at 更早者优先。
再相同则 id 更小者优先。
```

说明：

- 折扣券、封顶折扣券不能只看券面配置，需要结合本单金额动态计算实际优惠金额。
- 最优券选择只在当前订单可用券范围内进行；不满足车队、城市、产品线、时间、金额门槛的券不参与排序。

### 9.10 退款与退券

已确认：

- 支付失败时，立即释放已锁定优惠券。
- 全额退款时，退乘客优惠后实付金额。
- 全额退款后，优惠券恢复为 `UNUSED`；如果退款发生时优惠券已过有效期，则置为 `EXPIRED`。
- 部分退款本期不支持，不做优惠金额自动分摊。
- 如果后续出现部分退款需求，需要单独设计退款金额、优惠分摊、券状态恢复规则。

一期口径：

```text
支付失败：释放券。
全额退款：退乘客实付金额，券恢复 UNUSED；如果已过期则变 EXPIRED。
部分退款：一期不支持。
```

说明：

- 支付失败表示订单没有形成有效支付，不应占用用户券。
- 全额退款表示本单优惠使用结果撤销，但不能让已过期的券重新变成可用券。
- 部分退款涉及优惠分摊和收入分配重算，本期暂不进入自动化流程。

### 9.11 特殊活动规则

已确认：

- 特殊活动必须经过运营参与，并且仍需与车队达成一致后才能开启。
- 特殊活动可以不在后台页面中可见，本期不强制做后台配置入口。
- 平台主要通过 banner 图形式，让乘客进入活动页。
- 活动页可以承接特殊优惠券领取、活动说明、图片展示等能力。
- 特殊活动可以通过配置文件、Redis、`rule_config` 或发版方式开启。
- 活动结束后的配置下线方式可以按具体活动处理，本期不要求后台自助下线。
- 即使后台不可见，用户领券、持券、核销、订单结算仍必须落表，不能只依赖前端活动状态。

一期口径：

```text
特殊活动必须有 activity_code。
特殊活动必须经过运营参与，并与车队确认。
特殊活动后台可不可见。
乘客入口主要通过 banner 图进入活动页。
特殊活动可通过配置或发版开启。
用户领券、持券、核销、订单结算必须落表。
```

`activity_code` 字段本期作为预留字段：

- 常规登录弹框领取的普通券可以为空。
- 特殊活动券需要关联 banner、活动页、配置或订单排查时再填写。
- 建议放在 `coupon_template.activity_code`。
- 本期不强制做活动后台，也不强制每张券都有活动编码。

### 9.12 后台页面范围

已确认：

- 优惠券模板由唯一超管账号创建。
- 创建后，相关车队可以在后台看见该优惠券模板。
- 车队无权修改优惠券模板。
- 如果车队发现配置错误，需要向运营反馈，由运营与车队重新确认后，再由超管调整。
- 优惠券需要有启用/停用开关。
- 模板创建后不应立即随意启用，必须在运营所在公司与车队商量无误后再启动。
- 不做模板导出。
- 可查看领取量、使用量、优惠总额等统计信息，方便车队了解活动执行情况。

一期后台最小能力：

```text
模板列表
超管创建模板
超管启用/停用模板
查看领取数、使用数、优惠总额
车队只读查看模板和统计
不支持车队修改
不支持模板导出
```

### 9.13 数据域与权限

已确认：

- 本期不单独设计复杂优惠券数据域。
- 复用现有后台账号体系与计价规则可见范围。
- 登录者当前能看到几条计价规则，就能点进去查看这些计价规则下是否存在优惠券方案。
- 除超管外，其他账号都无权操作优惠券的新增、删除、修改、启用、停用。
- 超管负责优惠券方案的创建、调整、启用、停用等全部写操作。
- 非超管账号只读查看，不做增删改。

一期口径：

```text
优惠券可见范围 = 计价规则可见范围。
能看到计价规则，就能查看该规则下的优惠券方案。
只有超管有优惠券写权限。
非超管只读。
```

### 9.14 历史规则快照

已确认：

- 用户领券时，`user_coupon` 需要保存领券时的优惠券模板规则快照。
- 订单使用优惠券时，需要保存本单实际使用券、实际优惠金额、计算口径快照。
- 结算表需要保存平台服务费、承运侧收入等金额快照。
- 历史订单解释必须以订单发生时的快照为准，不能依赖后续被修改的模板配置。

一期口径：

```text
user_coupon 保存领券时规则快照。
trip_order_settlement 保存用券时结算快照。
```

快照目的：

- 模板后续被修改、停用或下架时，不影响已领取券和历史订单解释。
- 金额交易链路可追溯，能解释当时为什么优惠这么多、平台服务费是多少、承运侧收入是多少。
- 发生退款、投诉、对账时，不需要反查当前模板配置来推断历史金额。

## 10. 当前表设计与新方案的差距

昨天的表存在以下差距：

| 差距 | 影响 |
| --- | --- |
| `user_coupon` 没有 `coupon_type` | 用户券无法稳定识别固定减免/折扣券 |
| `user_coupon` 没有 `discount_rate` | 折扣券无法快照 |
| `user_coupon` 没有 `max_discount_amount` | 封顶折扣无法快照 |
| 旧方案使用 `owner_type / owner_id` | 当前已确认直接使用 `company_id`，不需要泛化归属 |
| 没有 `per_user_limit` | 无法限制每人领取 |
| `issue_type / source_type` 旧枚举不准确 | 需改为 LOGIN_CLAIM / LOGIN_POPUP，并预留 BANNER / AD / ACTIVITY / CONFIG |
| 没有 `activity_code` | 特殊活动无法串联 banner、活动页、配置与订单排查 |
| 没有 `rule_config / rule_snapshot` | 特殊活动没有扩展口，历史金额也缺少规则快照 |
| 没有发布状态字段 | 无法表达草稿、已发布、已下架 |
| 代码只按 `discount_amount` 算 | 折扣券实际不支持 |
| 最优券只按 `discount_amount` 排序 | 折扣券需要按本单动态优惠金额排序 |
| 结算表没有服务费字段 | 无法落地平台 5% 服务费口径 |

### 10.1 一到十复核结论

以下按当前讨论结果，整理为 10 个大点，便于后续拆正式 PRD/TECH：

1. **功能定位已确认**：优惠券不是单纯钱包功能，而是 `calculate` 侧的营销计价规则；钱包只负责展示乘客已持有的券和入口。
2. **规则边界已确认**：优惠券不要塞进 `fare_rule`，而是与基础计价规则并列；后台可以从计价规则页面进入优惠券方案查看/超管配置流程。
3. **车队归属已确认**：本期不引入 `fleet_id`；`company_id` 就表示当前系统里的公司+车队承运单元。计价规则、司机归属、订单承运方、优惠券适用车队统一使用 `company_id`。
4. **资金风险已确认**：两段式异步派单可能导致预估阶段的 `company_id/fare_rule_id` 与最终承运司机的 `company_id` 不一致。优惠券锁定、核销、支付前确认价、结算快照必须以最终订单 `company_id` 为准。
5. **券类型已确认**：本期内建固定金额减免、比例折扣、封顶折扣、固定开始/结束时间、城市、产品线；其它复杂活动走特殊规则预留。
6. **发券责任已确认**：不存在平台券；优惠券归属车队，成本和经营责任全部由发券车队承担。运营只能建议活动，是否发布、发布什么内容在线下沟通清楚，系统内由唯一超管执行发布。
7. **领取方式已确认**：本期常规券在用户登录时搜索可领取券，弹框询问是否一键领取全部；券实例绑定 `passenger_id/user_id`，不绑定手机号，用户换手机号不丢券。
8. **领取/使用限制已确认**：模板必须有总发放上限 `total_count`，默认每人限领 1 张；领完隐藏，领过也隐藏。每单最多用一张券，自动选最优，用户可选择不用券，后续也不做券叠加。
9. **金额与结算已确认**：平台服务费 = 乘客优惠后实付车费 * 5%；承运侧收入 = 乘客实付车费 - 平台服务费。本期只算到承运侧收入，不拆司机最终收入和车队收费。
10. **后台与快照已确认**：优惠券模板由超管创建、启用、停用；非超管只读，且可见范围复用计价规则可见范围。领券、用券、结算都需要快照，历史订单解释以快照为准。

当前已移除的复杂字段：

- 不做系统内发布商讨环节。
- 不记录运营确认人、车队确认人、确认时间、确认凭证、责任承担说明、运营建议说明等字段。
- 发布状态只保留系统执行状态：`DRAFT / PUBLISHED / OFFLINE`。
- `activity_code` 作为预留字段，常规券可为空，特殊活动券需要时再填写。

## 12. 暂定结论草案

如果后续没有反对意见，可以把一期优惠券目标定义为：

```text
一期建设车队自定义营销优惠券能力。

优惠券模板归属车队 company_id，不存在平台券。优惠券是否发布、发布什么内容，由运营所在公司与车队在线下会议或邮件中沟通清楚；系统不承载商讨流程，只由唯一超管账号在系统里执行发布，生成正式可领取、可核销的优惠券方案。

本期支持固定金额减免券、比例折扣券、封顶折扣券，并配置固定有效期、城市、产品线、发放总量和每人限领数量。

限制最大优惠金额、最低折扣率、同一时间启用数量等硬阈值，本期暂不做；下架功能暂定支持；复制模板类提效能力暂不做。

优惠券归属车队，优惠成本与经营责任全部由发券车队承担。运营只能提出活动建议和协助发布流程，不能绕过车队单方面发券。

订单结算时，calculate 根据订单上下文计算可用券与优惠金额；order 保存用券和结算快照；平台服务费按乘客优惠后实付车费的 5% 计算。

特殊活动券通过 rule_config、配置文件或 Redis 预留扩展，具体活动也应先在线下沟通清楚；系统不做活动商讨流程，但用户持券、核销和订单结算必须落表。
```
