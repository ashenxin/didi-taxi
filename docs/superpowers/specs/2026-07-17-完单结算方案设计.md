# 完单结算方案设计

> 日期：2026-07-17
>
> 状态：已实现（MVP 本地模拟闭环）
>
> 实施计划：[完单结算实施计划](../plans/2026-07-17-完单结算实施计划.md)；接口文档：[完单结算接口说明](../../api/完单结算接口说明.md)
>
> 适用范围：乘客端、司机端、`order-service`、`calculate-service`、`wallet-service`、`map-service`、`passenger-api`、`driver-api`

## 1. 目标

本设计把司机完单后的最终计价、优惠、免密支付、主动支付、结算状态、乘客展示和再次下单限制串成一条可恢复、可追踪且不会重复扣款的链路。

核心目标：

- 行程结束与资金结算解耦，司机完单不等待支付完成。
- 最终金额由服务端计算，优惠后金额才是支付金额。
- 免密扣款失败后由乘客主动选择支付宝或微信完成支付。
- 明确支付失败后不进行后台定时自动扣款。
- 支付结果未知时只查询原交易，不创建第二笔支付。
- 上一单未结清时禁止创建新订单，并提供可执行的处理入口。
- 同一订单允许多次支付尝试，但最多只能确认一次成功。

## 2. MVP 边界

### 2.1 本期包含

- 服务端最终计价。
- 本地 mock 规划距离、预计时长和实际计费时长，并冻结数据来源和版本。
- 自动选择并锁定优惠金额最大的可用优惠券。
- 支付金额边界校验及计算，异常金额不得静默归零或进入支付。
- 逻辑渠道为支付宝、微信的 mock 免密支付。
- 免密失败后的支付宝、微信 mock 主动支付及内部 mock 收银台。
- 独立结算查询接口。
- 结算状态通知和乘客端展示。
- 未结清订单拦截下单。
- 支付幂等、支付结果查询和人工运营兜底。

### 2.2 本期不包含

- 平台余额、授信、垫付、借款、分期或欠费继续叫车。
- 银行卡及支付宝、微信之外的支付渠道。
- 高德等外部地图 API、真实 GPS 轨迹和服务端时间戳计费。
- 支付宝、微信沙箱或生产渠道，真实商户签约、证书、SDK、验签、公网回调和渠道对账。
- 支付明确失败后的后台定时自动扣款。
- 常规退款、部分退款、组合支付、分账、发票和调账产品流程。重复扣款等资金安全异常仍必须通过原支付渠道退款并告警。
- 司机金额展示，以及司机/车队分成；这些能力尚未实现。
- 最终计价公式和目的地变更规则的重新设计。本流程复用现有计价规则算法，计价输入使用本规格确定的本地 mock 指标。

## 3. 核心业务口径

结算顺序固定为：

```text
服务端最终计价
→ 选择并锁定优惠券
→ 固化优惠前金额、优惠金额和应付金额
→ 尝试免密支付
→ 成功则结清；失败则等待乘客主动支付
```

金额定义：

```text
finalAmount     = 优惠前最终车费
discountAmount  = 本单优惠金额
payableAmount   = finalAmount - discountAmount
paidAmount      = 渠道确认支付成功的金额
```

司机端提交的 `distanceKm`、`durationMin` 或 `finalAmount` 不能作为结算依据。司机完单只表达“结束行程”。

### 3.1 本地 mock 计价指标

本期不调用外部地图 API，也不以 `finishedAt - startedAt` 作为计费时长：

```text
billingDistanceMeters = 下单时冻结的本地 mock 规划距离
billingDurationSeconds = 服务端生成并冻结的 mock 实际计费时长
distanceSource = LOCAL_MOCK_ROUTE
durationSource = LOCAL_MOCK_TRIP
```

- 下单时 `MockRouteProvider` 根据起终点和配置生成稳定的 `plannedDistanceMeters`、`plannedDurationSeconds`，相同输入和版本不得随机漂移。
- 完单结算首次执行时，`MockTripMetricsProvider` 根据订单号、规划数据和 mock 配置生成 `mockActualDurationSeconds`；默认可以等于规划时长，测试可注入更长或更短的场景。
- mock 实际计费时长由服务端提供器生成，司机客户端不能提交或覆盖。
- 首次生成后立即固化；重复完单、消息重放和结算重试必须读取原快照，不能重新生成。
- `startedAt`、`finishedAt` 继续用于行程状态和审计时间线，但不参与本期费用计算。
- 未来接入地图或 GPS 时新增数据提供器和来源枚举，历史 mock 订单继续按原快照复算。

### 3.2 金额范围与异常处理

所有金额必须先校验，再计算或支付，不能使用 `max(finalAmount - discountAmount, 0)` 把异常负数静默修正成零元单。

MVP 金额约束：

```text
0.01 ≤ finalAmount ≤ 10,000.00
0.00 ≤ discountAmount ≤ finalAmount
payableAmount = finalAmount - discountAmount
0.00 ≤ payableAmount ≤ finalAmount
支付成功时 paidAmount = payableAmount
```

- 单笔优惠前车费上限通过配置项管理，MVP 默认 `10,000.00` 元，后续可以按城市或产品调整。
- 金额统一按人民币元保存，使用 `BigDecimal`，最终金额采用 `HALF_UP` 舍入到两位小数。
- 优惠前车费必须大于零；合法优惠可以使 `payableAmount` 恰好为零。
- 金额先按统一规则舍入到两位小数，再执行范围和关系校验；任一金额为空、为负、超过上限、优惠大于车费或金额关系不成立时，均不得创建支付尝试。
- 异常订单保持 `CALCULATING`，记录 `failureCode=AMOUNT_OUT_OF_RANGE` 和原始计算摘要，触发运营告警并提示乘客联系运营。
- 运营修复计价数据后重新推进原结算任务，不能手工绕过金额校验。

## 4. 三段式行程与结算展示

### 4.1 第一段：行程结束

司机完单成功后：

- `orderStatus` 进入 `FINISHED`。
- 司机端立即显示“行程已结束”。
- 乘客首页立即显示“行程已结束”。
- 完单接口只承诺行程已结束、结算任务已可靠登记，不承诺支付成功。

### 4.2 第二段：结算处理中

乘客“我的订单”显示：

- `CALCULATING`：费用结算中。
- `PAY_CONFIRMING`：支付结果确认中。

这两个状态均不提供重新计价或重新支付按钮。用户不能修复计价系统，也不能在支付结果未知时创建第二笔支付。

### 4.3 第三段：支付结果

- `PAYMENT_REQUIRED`：待支付，展示应付金额、支付宝、微信和联系运营入口。
- `PAID`：支付成功，展示优惠前金额、优惠金额和实付金额。

## 5. 状态模型

订单行程状态与结算状态分开保存：

| 结算状态 | 含义 | 用户操作 | 能否下新单 |
| --- | --- | --- | --- |
| `CALCULATING` | 最终计价、选券或结算快照处理中 | 无；后台恢复计价任务 | 否 |
| `PAY_CONFIRMING` | 支付请求已受理，但渠道结果未知 | 无；查询原支付交易 | 否 |
| `PAYMENT_REQUIRED` | 无免密、免密明确失败、主动支付失败或用户取消 | 选择支付宝或微信重新支付；必要时联系运营 | 否 |
| `PAID` | 金额、支付结果和优惠券状态均已固化 | 查看账单 | 是 |

零元订单不调用支付渠道。优惠券核销和结算快照完成后直接进入 `PAID`。

## 6. 完整数据流

### 6.1 完单与可靠触发

`order-service` 在同一个本地事务内：

1. 使用 CAS 将订单从 `STARTED` 推进到 `FINISHED`。
2. 创建或初始化 `trip_order_settlement`，状态为 `CALCULATING`。
3. 写入订单事件。
4. 写入结算 Outbox 事件。

事务提交后立即向司机端返回“行程已结束，费用结算中”。Outbox 事件由现有投递机制发送，结算消费者第一阶段放在 `order-service` 内，不新增独立结算微服务。

### 6.2 最终计价与用券

结算消费者按 `orderNo` 幂等执行：

1. 读取下单冻结的 mock 规划距离、预计时长、计价规则快照和版本。
2. 读取已有 mock 实际计费时长；首次结算时由 `MockTripMetricsProvider` 生成并固化。
3. 使用 mock 规划距离、mock 实际计费时长和冻结计价规则调用 `calculate-service` 获取优惠前最终车费。
4. 按 `HALF_UP` 将最终车费舍入到两位小数，校验其非空且处于 `(0.00, 10,000.00]` 配置范围内。
5. 以最终车费为门槛，自动选择优惠金额最大的可用券。
6. 优惠金额相同时，优先选择更早过期的券；仍相同时按用户券 ID 稳定排序。
7. 校验优惠金额非负且不大于最终车费，然后原子锁定优惠券。
8. 计算并再次校验 `payableAmount`，固化金额、计价指标及优惠券快照。

下单缺少规划指标、计价规则快照或版本时不得使用当前规则临时补算，订单保持 `CALCULATING` 并告警。计价失败或金额越界不产生支付单。若金额校验在锁券后失败，应补偿释放本次尚未形成有效账单的券。短暂系统错误可以自动恢复计价任务；长期失败保持 `CALCULATING`，提示乘客联系运营。乘客不能点击重新计价。

### 6.3 免密支付

`payableAmount > 0` 时，`wallet-service` 查询乘客默认有效的免密协议：

- 有有效协议：创建 `AUTO_PAY` 支付尝试并调用对应的 `MockPaymentChannel`；测试配置可以控制成功、失败或结果待确认。
- 无有效协议：不调用渠道，结算进入 `PAYMENT_REQUIRED`。
- 渠道明确成功：进入支付成功收尾。
- 渠道明确失败：进入 `PAYMENT_REQUIRED`。
- 请求超时或结果未知：进入 `PAY_CONFIRMING`，查询原渠道交易。

明确支付失败后不进行后台定时自动扣款。

### 6.4 主动支付

`PAYMENT_REQUIRED` 状态下，乘客可以自由选择支付宝或微信：

1. 前端携带新的 `Idempotency-Key` 请求主动支付。
2. 服务端验证订单归属、结算状态和固化金额。
3. `wallet-service` 创建 `MANUAL` 支付尝试。
4. 前端打开返回的内部 mock 收银台地址。
5. mock 收银台允许测试人员选择成功、失败、用户取消或结果待确认；待确认尝试可以继续解析为成功或失败。
6. mock 回调沿用正式状态机入口推进钱包和订单结算状态。
7. 用户取消或渠道明确失败后继续保持 `PAYMENT_REQUIRED`。

主动支付不要求用户先签免密协议，不重新计价、不重新选券，也不接受客户端传入支付金额。

mock 支付能力只允许在 `local/dev/test` 环境或显式安全的演示配置中开启。非允许环境开启 mock 支付时应用必须拒绝启动，避免把模拟成功误当成真实收款。

### 6.5 支付成功收尾

支付成功后：

1. `wallet-service` 持久化成功交易及渠道交易号。
2. 有优惠券时将 `LOCKED` 核销为 `USED`。
3. `order-service` 校验 `paidAmount == payableAmount`。
4. 结算快照进入 `PAID`，记录成功 `paymentNo`、`paidAmount` 和 `paidAt`。
5. 发送 `ORDER_CHANGED`，乘客端重新查询结算结果。
6. 解除该订单对下一次下单的限制。

支付成功后核券或写结算快照失败时，只重试收尾步骤，绝不再次发起支付。

## 7. 优惠券失败处理

优惠券在最终金额固化后是账单的一部分：

- 免密支付失败转主动支付时，优惠券继续保持 `LOCKED`。
- 主动支付失败或用户取消时，优惠券继续保持 `LOCKED`。
- 主动支付始终支付已经固化的 `payableAmount`。
- 支付成功后将优惠券核销为 `USED`。
- 本期不提供用户自行取消未结清账单并释放优惠券的能力。

不能在免密失败时立即释放优惠券，否则账单优惠金额与优惠券实际状态会不一致。

## 8. 下单前未结清校验

### 8.1 拦截规则

创建订单必须同时满足：

```text
不存在进行中的订单
并且
不存在 FINISHED 但结算状态非 PAID 的订单
```

以下情况均禁止下单：

- 行程仍在进行中。
- `FINISHED + CALCULATING`。
- `FINISHED + PAY_CONFIRMING`。
- `FINISHED + PAYMENT_REQUIRED`。
- `FINISHED` 但结算记录缺失或不完整。

系统正常业务约束是一名乘客最多存在一笔阻塞下单的订单。接口仍通过明确的 `orderNo` 定位订单，不能依赖数据库中“刚好只有一笔未结清”来推断支付目标。

### 8.2 校验位置

- `passenger-api` 可以预检查，以便尽早展示友好提示。
- `order-service` 必须在创建订单事务内执行权威校验，防止绕过 BFF。
- 并发创建请求必须通过乘客级串行化或等价数据库约束保证，不能只依赖一次无锁 `count` 查询。
- 未结清校验依赖的内部服务异常时采用失败关闭：暂时拒绝下单，不放过可能的欠费订单。

### 8.3 拦截响应

```json
{
  "code": 409,
  "error": "UNSETTLED_ORDER",
  "message": "您有一笔待支付订单，请结清后再叫车",
  "data": {
    "blockingOrderNo": "T202607170001",
    "settlementStatus": "PAYMENT_REQUIRED",
    "action": "GO_TO_PAYMENT"
  }
}
```

`CALCULATING` 和 `PAY_CONFIRMING` 返回相应状态与文案，不错误展示“立即支付”。

## 9. 服务职责

| 服务 | 负责 | 不负责 |
| --- | --- | --- |
| `driver-api` | 接收司机完单、身份透传、返回行程结束结果 | 计算车费、编排支付 |
| `order-service` | 订单状态机、Outbox、结算编排、结算快照、未结清拦截 | 复制计价公式、直接修改钱包或券数据库 |
| `calculate-service` | 最终计价、选券、锁券、核销和必要补偿 | 创建支付交易 |
| `map-service` | 提供稳定的本地 mock 规划距离和预计时长 | 决定最终车费或支付状态 |
| `wallet-service` | 免密协议、支付尝试、mock 渠道、mock 收银台、回调、交易查询和幂等 | 决定车费或优惠金额 |
| `passenger-api` | 聚合乘客接口、鉴权、结算展示、主动支付入口和通知 | 持久化跨服务结算工作流 |

## 10. 对外接口

### 10.1 查询结算详情

```http
GET /app/api/v1/orders/{orderNo}/settlement
```

职责：只读查询某笔订单的结算状态和账单，不发起重新计价或支付。

响应示例：

```json
{
  "settlementStatus": "PAYMENT_REQUIRED",
  "originalFare": 35.60,
  "discountAmount": 5.00,
  "payableAmount": 30.60,
  "paidAmount": 0.00,
  "couponName": "满30减5元券",
  "availableChannels": ["ALIPAY", "WECHAT"],
  "message": "请支付上一笔订单后继续叫车"
}
```

订单列表返回 `settlementStatus` 摘要；完整金额和支付信息由本接口返回。

### 10.2 发起主动支付

```http
POST /app/api/v1/orders/{orderNo}/payments
Idempotency-Key: <客户端本次支付操作唯一键>
```

请求体：

```json
{
  "channel": "ALIPAY"
}
```

请求体只包含 `channel`。`orderNo` 来自路径，`passengerId` 来自登录态，金额和优惠来自结算快照，支付单号由服务端生成。客户端不能指定金额、乘客、优惠券、回调地址或支付单号。

服务端校验：

1. 订单属于当前乘客。
2. 结算状态为 `PAYMENT_REQUIRED`。
3. `payableAmount > 0`。
4. `finalAmount`、`discountAmount`、`payableAmount` 仍满足已固化的金额边界和相互关系。
5. 订单尚未支付成功。
6. 不存在结果待确认的支付尝试。
7. `channel` 是 `ALIPAY` 或 `WECHAT`。

响应示例：

```json
{
  "paymentNo": "PAY202607170001",
  "status": "PAYING",
  "invokePayload": {
    "type": "MOCK_CASHIER",
    "checkoutUrl": "/app/mock-pay/PAY202607170001"
  }
}
```

本期 `invokePayload` 返回内部 mock 收银台地址。未来真实渠道适配器可以在不改变主动支付业务请求的前提下返回支付宝订单串或微信预支付参数。

## 11. 数据模型调整

### 11.1 订单与结算快照

#### 11.1.1 计价输入快照

订单创建时必须保存：

- `plannedDistanceMeters`。
- `plannedDurationSeconds`。
- `distanceSource=LOCAL_MOCK_ROUTE`。
- 完整 `fareRuleSnapshot`。
- `fareCalculationVersion`。

结算首次执行时生成并保存：

- `mockActualDurationSeconds`。
- `durationSource=LOCAL_MOCK_TRIP`。
- mock 指标生成版本或配置摘要。

#### 11.1.2 `trip_order_settlement`

作为订单级权威结算快照，至少保存：

- 优惠前最终车费。
- 优惠券和优惠规则快照。
- 优惠金额和应付金额。
- 结算状态。
- 失败码、失败摘要和是否需要人工处理的标记。
- 最终成功支付单号；支付成功前保持为空。
- 实付金额、支付成功时间和结清时间。

结算状态使用明确字符串枚举，避免前端依赖无语义整数。

### 11.2 支付尝试

现有“一订单只能有一条支付单”的口径调整为：

- 一个订单可以有多条支付尝试记录。
- 每条记录保存 `triggerType=AUTO_PAY/MANUAL`、`channel`、`attemptNo`、幂等键、状态和渠道交易号。
- 同一订单最多允许一条记录最终确认 `SUCCESS`。
- `trip_order_settlement.paymentNo` 最终指向成功记录。
- 相同幂等键重复请求返回原支付尝试。

该模型允许用户在一次支付宝失败后改用微信，同时保留完整审计记录。

## 12. 支付并发与幂等

- 支付尝试的幂等键全局唯一。
- 渠道请求使用独立且稳定的渠道幂等号。
- 渠道回调可重复处理。
- `PAID` 后再次调用主动支付直接返回已支付，不调用渠道。
- `PAY_CONFIRMING` 时拒绝创建新支付尝试。
- 支付成功确认必须对订单级成功状态执行原子竞争，保证最多一笔成功。
- mock 测试中若两个支付尝试均提交成功结果，订单级原子竞争只接受第一笔，第二笔记录为重复成功异常并告警。未来接入真实渠道时，该异常还必须触发原路退款。

## 13. 失败恢复与运营处理

| 场景 | 系统处理 |
| --- | --- |
| 最终计价失败 | 保持 `CALCULATING`；可恢复计价任务；不产生支付单 |
| 金额为空、为负、越界或关系不成立 | 保持 `CALCULATING`；记录 `AMOUNT_OUT_OF_RANGE`；停止支付并告警 |
| 支付明确失败 | 进入 `PAYMENT_REQUIRED`；不后台自动重扣 |
| 支付结果未知 | 进入 `PAY_CONFIRMING`；查询原交易；不创建第二笔支付 |
| 主动支付取消或失败 | 返回 `PAYMENT_REQUIRED`；由用户再次选择渠道 |
| 支付成功后核券失败 | 只重试核券和结算收尾；不再次支付 |
| 通知失败 | 重试通知；HTTP 查询仍是权威结果 |

乘客连续支付失败或状态长时间异常时，页面展示“联系运营”。运营可以查询渠道交易、恢复异常状态或指导用户重新支付，但不能在没有渠道成功凭证时手工标记 `PAID`。

## 14. 通知与前端刷新

WebSocket 继续只发送通用 `ORDER_CHANGED`，不把金额或支付结果作为权威数据塞入推送。

通知节点：

1. `FINISHED + CALCULATING`：行程已结束，费用结算中。
2. `PAYMENT_REQUIRED`：待支付，可选择支付宝或微信。
3. `PAID`：支付成功。

前端收到通知后查询权威 HTTP 数据。订单列表展示结算摘要；进入结算页面或支付返回后调用独立结算详情接口。

## 15. 安全要求

- 所有乘客接口从登录态取得 `passengerId`。
- 查询和支付前校验订单归属。
- 客户端不能提交或覆盖应付金额、优惠金额和支付状态。
- 计价完成、结算快照写入和每次发起支付前都校验金额范围与金额关系。
- mock 结果回调必须校验支付操作令牌、订单号、支付单号、渠道、金额和当前状态；未来真实渠道适配器还必须验签并校验商户号、币种等渠道字段。
- mock 收银台和 mock 结果回调只能在允许环境使用，并通过短期、不可猜测的支付操作令牌限制为对应支付尝试。
- 日志不得记录完整支付凭据、渠道签名或敏感身份信息。
- 所有金额使用 `BigDecimal` 和固定舍入规则，数据库使用固定精度 `DECIMAL`。

## 16. 验收测试

至少覆盖以下场景：

1. 司机完单后立即进入 `CALCULATING`，首页显示行程结束。
2. 司机重复完单或并发完单只产生一份结算任务。
3. 计价失败时不创建支付尝试、不允许下新单。
4. 计价消息重复消费不会重复选券或支付。
5. 免密成功后进入 `PAID`，优惠券核销并允许下单。
6. 未开免密或免密明确失败后进入 `PAYMENT_REQUIRED`。
7. 明确支付失败后不存在后台定时自动扣款。
8. 主动支付可以自由选择支付宝或微信。
9. 主动支付不能提交或篡改金额、乘客或优惠数据。
10. 相同 `Idempotency-Key` 重复提交只产生一次支付尝试。
11. 支付结果未知时进入 `PAY_CONFIRMING` 并禁止第二笔支付。
12. 用户取消主动支付后回到 `PAYMENT_REQUIRED`。
13. 支付失败期间优惠券保持 `LOCKED`。
14. 支付成功回调重复到达不会重复核券。
15. 支付成功后核券失败不会再次扣款。
16. 支付宝、微信并发支付时订单级成功确认最多一次。
17. `FINISHED` 但结算记录缺失或不完整时仍禁止下单。
18. `CALCULATING`、`PAY_CONFIRMING`、`PAYMENT_REQUIRED` 均返回对应未结清提示。
19. `PAID` 后立即解除下单限制。
20. 零元订单不调用支付渠道，完成核券后直接进入 `PAID`。
21. 用户不能查询或支付其他乘客的订单。
22. 错过 WebSocket 通知后仍能通过 HTTP 查询正确结算结果。
23. `finalAmount` 为零、负数、空值或超过 `10,000.00` 元时不创建支付尝试并产生告警。
24. `discountAmount` 为负或大于 `finalAmount` 时不把应付金额静默归零。
25. `payableAmount` 恰好为零时按零元订单结清，边界值 `10,000.00` 元可正常进入支付。
26. 金额含超过两位小数时按统一规则舍入，并在舍入后重新校验金额关系。
27. 相同起终点和 mock 版本生成稳定的规划距离和预计时长。
28. mock 实际计费时长首次生成后，重复完单和结算重试读取同一快照。
29. 司机端提交的距离、时长和金额不参与最终计价。
30. `startedAt`、`finishedAt` 变化不改变已经冻结的 mock 计费时长。
31. 缺少规划指标、计价规则快照或版本时停止结算，不使用当前规则临时补算。
32. mock 收银台完整覆盖成功、失败、取消、结果待确认及待确认后的最终解析。
33. 非允许环境不能启用 mock 支付，整个 MVP 不调用外部地图或真实支付接口。

## 18. 已登记的下周高优先级后续设计

司机端金额展示不能直接把乘客实付金额或承运侧收入称为“司机收入”。下周需要单独设计车队/运营公司与司机之间的收入分配，并同步影响后台计价/结算规则和司机端展示。

已确定边界：

- 首期分成模式只支持 `FIXED_AMOUNT`（每单固定金额）和 `PERCENTAGE`（按比例）两种。
- 沿用既有口径：平台服务费按乘客优惠后实付金额的 5% 计算，`carrierIncomeAmount = payableAmount - platformServiceFeeAmount`；下周专项只继续拆分承运侧内部的车队/运营公司分成与司机收入。
- 后台需要能够配置或查看订单适用的分成规则，司机端需要基于订单分成快照展示可解释的金额。
- 分成结果必须按订单固化规则快照，不能因后台后续修改规则而改变历史订单。
- 分成金额继续遵守本规格的非负、上限、舍入和金额关系校验要求。
- 在独立分成设计定版前，司机端只能展示“订单总金额”，不能展示“司机净收入”“可提现金额”或类似承诺性字段。

独立分成设计必须先明确固定金额或比例规则以哪个金额科目为计算基数、优惠券成本承担、固定金额越界处理、比例范围、尾差归属、规则生效时间、退款冲正和运营查询口径。以上内容不进入本期乘客支付实现计划。
