# 乘客账号换号与注销统一生命周期设计

> 日期：2026-07-20  
> 状态：设计已确认；P1～P7 代码链路已贯通，等待目标环境数据核验、真实故障演练与生产灰度
> 适用范围：乘客账号 `customer`；司机与后台账号不在本期共用同一套业务流程

## 1. 决策摘要

本方案采用“乘客域持久化编排 Saga + Transactional Outbox + 前置检查责任链 + 参与者注册表 + 统一生命周期门禁”的组合。

核心决策如下：

1. `passenger` 是乘客账号生命周期、生命周期版本和认证代次的权威来源。
2. `passenger-api` 只负责端侧身份、验证码交互、DTO 转换和 Operation 查询，不再直接串行编排订单、结算、钱包、券与积分。
3. `order`、`wallet`、`calculate` 等服务继续维护各自业务事实，生命周期中心不得直接修改其数据库。
4. 责任链只用于只读资格检查；拦截器只用于身份、审计上下文和基于动作码的生命周期门禁；Saga 负责状态推进、重试、超时和人工处置。
5. 注销不是单请求同步事务。正式提交后返回 `operationNo + status`，由后台可靠完成。
6. 注销在不可逆清理开始前允许撤销；一旦进入不可逆阶段，只允许前向完成或转人工，不恢复账号。
7. 换号保持原 `customer.id`，只更新同一行当前手机号；订单、钱包、优惠券和积分不迁移。
8. 注销只有最终进入 `CANCELLED` 时才设置 `is_deleted=1` 并释放手机号。
9. 流程模板使用随应用发布的版本化 YAML，不使用数据库计划定义表，也不支持运行时热更新。
10. Operation 只保存 `plan_code + plan_version + plan_digest`，不保存完整 `plan_snapshot`；实际步骤与非敏感配置固化在 `account_lifecycle_step`。
11. `customer_phone_binding_history` 保持当前设计，同时保留手机号密文和 HMAC 历史；它只记录绑定历史，不负责资产归属或当前手机号唯一性。

## 2. 背景与当前问题

当前注销逻辑位于 `passenger-api` 的 `PassengerSettingsService`：

1. 分页加载全部订单并判断非终态订单。
2. 调用 order 检查未结清结算。
3. 调用 calculate 检查锁定优惠券。
4. 调用 passenger 将 `customer.is_deleted` 更新为 1。
5. 尽力作废未使用券并清零积分。
6. 最后递增 Redis token version。

该实现存在以下问题：

- 每增加一个业务域都需要继续修改 BFF 注销方法，业务不断横向膨胀。
- passenger 数据库变更与 Redis token version 递增不是一个事务，可能出现账号已变更但旧 Token 仍有效。
- 注销检查与并发下单之间没有写栅栏，可能出现检查通过后新建订单。
- 账号先删除，券与积分仅尽力清理；调用失败后没有持久化补偿。
- wallet 没有参与注销，免密协议和未来真实渠道授权可能继续有效。
- 已建立 WebSocket 只在握手时检查 token version，不会因换号或注销主动关闭。
- 当前 OTP 使用读取后删除方式，并发请求可能重复消费。
- JWT 携带可变手机号，优惠券手机号 HMAC 风控依赖该快照，身份凭据与业务规则发生耦合。

## 3. 目标与非目标

### 3.1 目标

- 把换号、注销代码收束到明确的账户生命周期边界。
- 支持订单、钱包、券、积分以及后续退款、对账、发票等领域按统一契约接入。
- 保证敏感账号变更、认证失效与本地 Outbox 同事务提交。
- 保证每个跨服务步骤可幂等、可重试、可查询和可人工处置。
- 防止注销期间新增订单、资产或外部授权。
- 保留订单、支付、退款、券积分流水等必要业务与审计记录。
- 允许逐步从当前实现迁移，不要求一次性切换。

### 3.2 非目标

- 本期不构建通用 BPMN 或低代码工作流平台。
- 本期不允许后台任意增删 `REQUIRED` 步骤。
- 本期不把乘客、司机、后台管理员合并为一张万能账号表。
- 本期不做注销后账号恢复。
- 本期不物理删除订单、支付、结算、券积分流水。
- 本期不改变既定的“换号保持 customer.id、注销后重新注册产生新 customer.id”口径。
- 本期暂不收缩 `customer_phone_binding_history.phone_ciphertext`。

## 4. 系统边界

### 4.1 passenger-api

负责：

- 从可信身份上下文获得 `customerId`。
- 处理 OTP 发放与用户输入。
- 接收 `Idempotency-Key`、`expectedLifecycleVersion`。
- 调用 passenger 生命周期应用服务。
- 返回结构化 blocker、Operation 状态和可执行动作。
- 为 `CANCELLING` 用户处理受限生命周期会话。

不负责：

- 保存 Saga 状态。
- 直接修改领域服务数据。
- 通过大方法依次调用所有业务服务完成注销。

### 4.2 passenger

负责：

- `customer.lifecycle_status`、`lifecycle_version`、`auth_epoch`。
- Operation、Step、Blocker、Event、Outbox。
- 读取 YAML 计划并生成运行步骤快照。
- 生命周期状态推进与 CAS。
- 参与者端口、命令投递、结果回执和主动对账。
- 恢复扫描与人工处置入口。

第一阶段在现有 passenger 服务内建立独立 `account-lifecycle` 包，不新建部署单元。若后续团队、流量或治理边界要求，再提取独立服务。

### 4.3 领域参与者

- `ORDER`：在途订单、未结算、人工处理中的结算与后续退款/发票义务。
- `WALLET`：支付处理中、回调处理中、免密协议、渠道解约、拒付与对账风险。
- `CALCULATE`：锁券、未使用券作废、积分清零及账本流水。
- `IDENTITY`：手机号、OAuth、实名资料、绑定历史和数据保留登记。
- `SESSION`：普通 HTTP 会话、受限会话、WS 票据和连接撤销。
- `ACCOUNT`：最终注销本地事务。

每个领域只裁决自己的事实，不把业务规则复制到生命周期中心。

## 5. 状态模型

### 5.1 账户生命周期

```text
ACTIVE -> CANCELLING -> CANCELLED
             |
             +-> ACTIVE（仅不可逆动作开始前撤销）
```

现有 `customer.status` 继续表达正常、冻结等业务状态；新增 `lifecycle_status` 表达生命周期，避免枚举笛卡尔积。

### 5.2 Operation 状态

```text
REQUESTED
  -> FENCED
  -> VALIDATING
  -> BLOCKED -> VALIDATING
  -> EXECUTING
  -> RETRY_PENDING -> EXECUTING
  -> MANUAL_REVIEW -> EXECUTING / COMPLETED
  -> COMPLETED

FENCED / BLOCKED -> ABORTED
```

- `REQUESTED`：已原子消费 OTP 并创建 Operation。
- `FENCED`：账号进入 `CANCELLING`，普通认证代次失效。
- `VALIDATING`：栅栏后权威复检。
- `BLOCKED`：存在可消除义务，允许解阻动作。
- `EXECUTING`：开始执行领域清理。
- `RETRY_PENDING`：暂时失败，等待恢复。
- `MANUAL_REVIEW`：不能安全自动处理。
- `COMPLETED`：必要动作全部成功并完成最终注销。
- `ABORTED`：不可逆动作前用户撤销。

### 5.3 Step 状态

```text
PENDING / RUNNING / SUCCEEDED / BLOCKED /
RETRY_PENDING / MANUAL_REVIEW / SKIPPED / CANCELLED
```

步骤分级：

- `PRECONDITION`：在途订单、未结清支付等前置条件。
- `REQUIRED`：关闭免密、作废券、积分清零等必须成功动作。
- `RETENTION`：登记保留或匿名化策略。
- `POST_ACTION`：WS 主动关闭、普通通知等可在核心安全已建立后继续重试的动作。
- `FINALIZE`：最终设置 `CANCELLED/is_deleted=1`。

## 6. 注销完整流程

### 6.1 只读预检

正式提交前调用同步责任链，返回结构化 blocker，不改变账户状态。

目的：避免用户有明显在途订单时立即进入受限状态。

### 6.2 正式提交与建栅栏

在 passenger 一个本地事务中完成：

1. 原子消费 `ACCOUNT_CANCEL` OTP。
2. 校验 `Idempotency-Key + request_hash`。
3. 使用 `expectedLifecycleVersion` CAS 更新账号。
4. `ACTIVE -> CANCELLING`。
5. `lifecycle_version + 1`。
6. `auth_epoch + 1`。
7. 创建 Operation 和 Step 快照。
8. 写生命周期 Event。
9. 写 Outbox。

事务失败时不得产生部分状态。

### 6.3 受限生命周期会话

普通 Token 因 `auth_epoch` 变化失效。当前设备获得短期受限会话，只允许：

- 查询订单、账单、退款和发票进度。
- 取消或完成现有订单。
- 支付欠款。
- 提交必要的退款/争议材料。
- 联系客服。
- 在允许阶段撤销注销。

禁止：

- 新下单。
- 领券、签到、积分兑换。
- 新签免密或绑卡。
- 再次换号。
- 绑定新的 OAuth 或修改实名。

### 6.4 栅栏后复检

建立栅栏后再次同步查询 ORDER、WALLET、CALCULATE、IDENTITY。

如果预检与栅栏之间有并发订单或支付请求，复检会把 Operation 置为 `BLOCKED`。本方案不引入跨服务分布式锁，而是使用：

- 账户栅栏。
- 领域写入口生命周期投影门禁。
- 栅栏后复检。
- 最终提交前再检查。

共同保证最终不会错误注销存在义务的账号。

### 6.5 不可逆执行

进入第一组不可逆 `ACTION` 前，原子设置 `irreversible_started=1`。之后：

- 用户不能撤销。
- 所有失败只做前向重试或人工处理。
- 不因清券、积分或渠道异常而恢复账号。

### 6.6 最终完成

必要步骤全部成功后，本地事务完成：

```text
lifecycle_status = CANCELLED
lifecycle_version + 1
auth_epoch + 1
is_deleted = 1
cancelled_at = now
current_lifecycle_operation_no = null
手机号历史 ACTIVE -> RELEASED
Operation -> COMPLETED
写 Event + Outbox
```

此时生成列 `phone_active` 才变为 `NULL`，手机号允许注册为新的 `customer.id`。

## 7. 换号流程

换号使用同一 Operation/Step 基础设施，但账户保持 `ACTIVE`，不调用订单、钱包、券积分迁移。

核心事务完成：

1. 原子消费 `PHONE_CHANGE_NEW_PHONE` OTP。
2. 校验新手机号与当前手机号不同。
3. 校验新手机号未被其他未注销账号占用。
4. 使用数据库唯一索引处理并发占用。
5. 更新同一条 `customer.phone`。
6. 原手机号历史改为 `REPLACED`，新增 `ACTIVE` 绑定版本。
7. `lifecycle_version + 1`、`auth_epoch + 1`。
8. 创建/完成 Operation、写 Event 与 Outbox。

`phone_active` 在同一条 UPDATE 后直接从旧手机号变成新手机号，不会通过中间 `NULL` 完成换号。

本期继续采用现有安全口径：有效登录态证明当前账号控制权，新手机号 OTP 证明新号码控制权；不新增旧手机号 OTP、人脸或客服申诉流程。

## 8. 数据模型

评审 SQL：

`passenger/src/main/resources/sql/passenger_account_lifecycle_patch.sql`

保留表：

- `account_lifecycle_operation`
- `account_lifecycle_step`
- `account_lifecycle_blocker`
- `account_lifecycle_event`
- `account_lifecycle_outbox`
- `customer_phone_binding_history`

不创建：

- `account_lifecycle_plan_definition`
- `account_lifecycle_plan_step_definition`

### 8.1 Operation 字段语义

- `operation_type`：用户要做什么，例如 `PHONE_CHANGE/ACCOUNT_CANCEL`。
- `status`：当前做到哪一步。
- `plan_code/version/digest`：本次采用哪套流程模板。
- `request_hash`：同一幂等键是否被换内容复用。
- `irreversible_started`：是否跨过可撤销边界。
- `row_version`：Operation 状态 CAS。

### 8.2 Event 与 Outbox

`account_lifecycle_event` 是只追加业务审计流水，回答“发生过什么、谁做的、为什么”。

`account_lifecycle_outbox` 是可靠消息投递队列，回答“哪条命令或事件尚未可靠发布”。它会更新发布状态、重试次数和错误，不替代审计流水。

一条业务 Event 可以产生多条 Outbox 命令；不是所有审计 Event 都需要跨服务发布。

Outbox 使用以下字段串联因果关系：

- `causation_event_id`：触发该消息的审计事件。
- `trace_id`：全链路追踪标识。

### 8.3 手机号绑定历史

`customer_phone_binding_history` 记录注册、换号和注销释放形成的版本化绑定事实。

它不负责：

- 当前手机号查询。
- 当前手机号唯一性。
- 用户登录。
- 订单和资产关联。
- 生命周期流程进度。

订单、钱包、券积分永远通过 `customer.id/passenger_id` 归属。

## 9. YAML 流程模板

配置文件：

- `passenger/src/main/resources/account-lifecycle/account-cancel-v1.yml`
- `passenger/src/main/resources/account-lifecycle/phone-change-v1.yml`

规则：

- 文件随应用包发布并纳入 Git。
- 不接配置中心热更新。
- 已发布 v1 不覆盖修改；流程变化新增 v2。
- YAML 只能引用 Java 白名单 participant。
- 禁止脚本、SQL、类名反射、外部 URL、密钥和敏感数据。
- 服务启动时校验 plan、step、participant、顺序和重试范围。
- 创建 Operation 时对规范化配置计算 SHA-256，保存 `plan_digest`。
- 每个实际 Step 与 `step_config` 固化到数据库。

Operation 不保存完整 `plan_snapshot`。

## 10. 参与者契约

### 10.1 同步检查

预检、栅栏后复检和最终检查采用内部 HTTP，只读返回：

```text
PASS
BLOCKED(blockers[])
UNKNOWN
```

服务异常、超时或 UNKNOWN 时失败关闭，不得按“无风险”处理。

### 10.2 异步执行

清理动作通过本地 Outbox 发布 Kafka 命令。命令至少包含：

```text
eventId
operationNo
stepCode
accountId
lifecycleVersion
attempt
occurredAt
```

不得传播 OTP、Token、密码、明文手机号或渠道密钥。

### 10.3 幂等与成功未知

每个参与领域在自己的数据库中以：

```text
operationNo + stepCode
```

建立唯一 Inbox。Inbox/幂等记录必须与本地业务副作用在同一个事务中提交。

如果领域执行成功但回执丢失，中心通过 `query(operationNo, stepCode)` 主动查询，不盲目重复产生外部副作用。

## 11. 风险分类

### 11.1 BLOCKER

- 非终态订单。
- 未结清或支付确认中的结算。
- 锁定优惠券。
- 退款、拒付、重复扣款、调账或对账争议。
- 后续发票、借贷、保险等未完成义务。

### 11.2 AUTO_ACTION

- 关闭本地和渠道免密协议。
- 作废未使用券并写动作流水。
- 清零积分、关闭积分账户并写负向流水。
- 撤销 OAuth。
- 撤销普通会话和 WS。

### 11.3 RETAIN

- 订单、订单事件和结算。
- 支付、退款、拒付和对账。
- 券和积分流水。
- 幂等记录和必要 Outbox/Inbox 记录。
- 发票、收入分配和冲正记录。

### 11.4 MANUAL

- 渠道免密解约长期失败。
- 重复成功支付或退款失败。
- 长短款、拒付和调账。
- 发票红冲异常。
- 司机/车队收入冲正异常。
- 需要合规或客服裁决的身份问题。

## 12. 统一门禁

业务接口使用稳定动作码，而不是各自写注销判断：

```text
RIDE_CREATE
ORDER_READ
ORDER_CANCEL
DEBT_PAYMENT
COUPON_CLAIM
BENEFIT_SIGN_IN
AUTO_PAY_SIGN
REFUND_READ
```

门禁输入：

```text
businessStatus + lifecycleStatus + tokenScope + actionCode
```

门禁分两层：

1. BFF Filter/Interceptor：快速拒绝并返回一致响应。
2. 高风险领域写入口的通用 `AccountWriteFence`：防止内部调用、延迟消息或绕过 BFF 的请求新增义务。

拦截器不得发起跨服务清理，也不得承担 Saga。

## 13. 认证、OTP 与内部安全

### 13.1 auth_epoch

- `customer.auth_epoch` 是数据库权威。
- Redis `passenger:tv:*` 降级为缓存投影。
- 缓存缺失时回源 passenger。
- 换号、注销建栅栏、注销完成等敏感事务内递增 epoch。
- Outbox 驱动缓存失效和 WS 主动关闭。

### 13.2 OTP

验证码按 Purpose 隔离：

- `LOGIN`
- `PHONE_CHANGE_NEW_PHONE`
- `ACCOUNT_CANCEL`

使用 Redis Lua 或等价原子机制完成校验与消费，禁止 GET 后 DELETE。

### 13.3 内部接口

生命周期内部接口必须增加服务身份：

- mTLS 或内部服务 Token。
- service audience/identity。
- Request ID 和防重放。
- 最小权限。
- 浏览器流量不得直接访问 internal 路径。

## 14. API 建议

```text
POST /app/api/v1/account-lifecycle/cancellations/precheck
POST /app/api/v1/account-lifecycle/cancellations
GET  /app/api/v1/account-lifecycle/operations/{operationNo}
POST /app/api/v1/account-lifecycle/operations/{operationNo}/abort
POST /app/api/v1/account-lifecycle/operations/{operationNo}/recheck

POST /app/api/v1/account-lifecycle/phone-changes/sms/send
POST /app/api/v1/account-lifecycle/phone-changes
```

正式注销提交成功返回 HTTP 202。旧 settings 接口在迁移期保留，但内部转调新 Lifecycle Application Service。

## 15. 失败处理与人工处置

- 临时失败：指数退避，进入 `RETRY_PENDING`。
- 超过自动阈值：进入 `MANUAL_REVIEW`。
- 管理员可以重新执行、查询渠道状态、确认线下处理、解除已经不存在的 blocker 或拒绝注销。
- 管理员不能跳过未关闭免密、未结清支付等资金安全步骤直接完成注销。
- 所有人工动作写 `account_lifecycle_event`，记录操作人、原因、凭证和前后状态。
- 核心提交后不做账号复活式补偿。

## 16. 观测与恢复

至少提供：

- 各 Operation 状态数量和停留时长。
- Step 成功率、重试次数、超时和人工处理数量。
- Outbox PENDING/PROCESSING/FAILED 积压。
- 按 operationNo/customerId/traceId 的完整轨迹。
- XXL-Job 恢复扫描。
- 渠道解约、券积分处理和会话撤销的领域对账。

告警重点：

- `CANCELLING` 超时。
- `RETRY_PENDING` 超过阈值。
- `MANUAL_REVIEW` 积压。
- Outbox FAILED。
- 已 `CANCELLED` 但领域投影仍允许新增业务。

## 17. 测试要求

必须覆盖：

- 注销预检后并发下单。
- 两个注销请求并发提交。
- 换号与注销并发。
- OTP 并发消费。
- passenger 提交后立即宕机。
- Kafka 不可用和 Outbox 恢复。
- 领域成功但回执丢失。
- 重复收到同一步命令。
- 部分领域成功、部分失败。
- 免密渠道长期不可用。
- 不可逆前撤销和不可逆后拒绝撤销。
- CANCELLING 状态动作权限矩阵。
- 同手机号注销后重新注册为新 customer.id。
- 已建立 WS 的主动关闭与重连拒绝。
- v1 Operation 运行期间发布 v2 YAML。
- YAML participant 缺失、步骤重复、FINALIZE 缺失时启动失败。
- 人工处理审计。

## 18. 迁移路线

### 阶段一：基础设施

- 增加 passenger 生命周期表和字段。
- 加载、校验 YAML 计划。
- 建立 Operation/Step/Event/Outbox 基础能力。
- 不接管线上注销。

### 阶段二：影子检查

- 新旧注销检查同时运行。
- 新流程只记录判断结果，不执行领域副作用。
- 对比订单、结算、锁券等结果差异。

### 阶段三：认证与会话

- 将 Redis token version 迁移为数据库 auth_epoch 权威。
- 接入原子 OTP。
- 实现受限生命周期会话和动作门禁。

### 阶段四：领域执行

- 接入 calculate 券积分。
- 接入 wallet 免密和支付风险。
- 接入 WS 主动关闭与领域投影。
- 使用 Inbox 保证参与者幂等。

### 阶段五：切换与清理

- 旧 settings 接口转调新流程。
- 观察稳定后删除 `PassengerSettingsService` 中旧编排代码。
- 保留只读兼容和历史 Operation 查询。

回滚只能停止受理新的换号/注销；已经进入不可逆阶段的 Operation 必须继续由新流程前向恢复。

## 19. 实施子项目拆分

正式实施计划按可独立验收的子项目拆分，避免一次改动全部服务：

1. 生命周期数据模型、YAML 计划加载与本地 Operation 状态机。
2. 数据库 auth_epoch、原子 OTP、普通/受限会话和 WS 撤销。
3. 动作码门禁、影子预检与 order 生命周期参与者。
4. calculate 券积分参与者及 Inbox 幂等。
5. wallet 支付风险和免密解约参与者。
6. Outbox/Kafka 回执、成功未知查询、XXL 恢复和后台人工处置。
7. 旧 settings 接口迁移、灰度切换与旧编排删除。

每个子项目都必须在进入下一项前具备独立测试、观测和回滚边界。

## 20. 验收标准

- 换号前后 `customer.id` 不变，历史订单和资产不丢失。
- 敏感变更、auth_epoch、Operation/Event/Outbox 同事务提交。
- 注销期间不能新增订单、券、积分或外部授权。
- 在途和未结清义务能以结构化 blocker 展示并解除。
- 任一参与服务或 Kafka 故障都不会永久丢失步骤。
- 重复命令不会重复清券、清积分或关闭渠道协议。
- 不可逆开始前可以撤销，之后不能恢复账号。
- 只有所有 REQUIRED 步骤成功后才释放手机号。
- 订单、支付、退款、对账、发票和流水在注销后仍可按旧业务号处理。
- 新业务接入只新增参与者实现、动作码和新 YAML 版本，不修改注销主流程条件分支。
