# 乘客账号生命周期 P3：动作门禁与 Order 参与者执行计划

## 1. 阶段目标与状态

P3 负责在 BFF 和 Order 领域建立统一动作门禁，并把 Order 建设为第一个标准生命周期
参与者，关闭“注销检查通过后又并发创建新订单”的竞态窗口。

**当前状态：代码实现已完成。** 生产强制启用前仍需在目标环境核验 P3 回填覆盖率，
并执行真实 MySQL 8 双连接并发验证。

## 2. 明确边界

- passenger-api 只做快速权限拦截，不能替代领域写门禁。
- Order 是订单事实和订单写入合法性的权威来源。
- P3 不执行 Calculate 券积分和 Wallet 支付清理。
- 影子预检只比较新旧 Order 风险，不改变旧 settings 的线上裁决。
- P3 只建设参与者，不在 P6 前执行完整注销编排。

## 3. 统一动作码

生命周期裁决输入统一为：

`businessStatus + lifecycleStatus + tokenScope + actionCode`

主要动作：

- `RIDE_CREATE`
- `ORDER_READ`
- `ORDER_CANCEL`
- `DEBT_PAYMENT`
- `COUPON_CLAIM`
- `BENEFIT_SIGN_IN`
- `AUTO_PAY_SIGN`
- `PHONE_CHANGE`
- `ACCOUNT_CANCEL`
- `WS_CONNECT`

`CANCELLING + LIFECYCLE_RESTRICTED` 允许查询订单、取消订单、支付欠款和管理注销，
拒绝下单、领券、签到、签约免密、换号和 WS。

未知状态、未知动作和认证状态不可用必须失败关闭。

## 4. Order 生命周期投影

Order 本地维护 passenger 生命周期投影，避免普通订单事务跨库读取 passenger。

核心字段：

- `customer_id`
- `business_status`
- `lifecycle_status`
- `lifecycle_version`
- `operation_no`
- `source_event_id`
- `row_version`

投影更新规则：

- 新版本覆盖旧版本。
- 相同版本、相同事实视为幂等。
- 相同版本、不同事实返回冲突。
- 旧版本事件判为 stale，不能倒退投影。
- 缺失、未知或过期投影对高风险写操作失败关闭。

## 5. 领域写栅栏

`AccountWriteFence` 必须位于 Order 本地事务边界内。

创建订单采用：

1. 锁定该乘客的 lifecycle projection。
2. 校验 ACTIVE 且版本有效。
3. 写订单、Event 和 Outbox。
4. 在同一事务提交。

注销参与者建立 Order 栅栏时使用同一投影行锁：

- 下单先获得锁：订单先提交，注销最终检查看到新订单并返回 BLOCKED。
- 注销先获得锁：投影先进入 CANCELLING，后续下单返回冲突。

这使“检查通过后并发下单”无法穿过领域事务边界。

## 6. Order 注销参与者

内部接口提供：

- 只读预检。
- 建立 Order 注销栅栏。
- 最终检查。
- 根据 `operationNo + stepCode` 查询既有结果。

参与者固定返回：

- `PASS`
- `BLOCKED`
- `UNKNOWN`

Blocker 使用稳定结构：

- `code`
- `resourceType`
- `resourceNo`
- `action`

活动订单、未结清支付义务等返回 BLOCKED；基础设施不可用或事实无法确认返回 UNKNOWN。

## 7. Inbox 与内部安全

`order_lifecycle_participant_inbox` 使用 `operationNo + stepCode` 幂等：

- 同键同请求摘要返回原结果。
- 同键不同请求摘要返回 409。
- 已经提交的领域副作用不能因回执丢失而重复执行。

内部接口受独立的 `ORDER_LIFECYCLE_INTERNAL_TOKEN` 保护。Token 只添加到专用
Lifecycle Client，不能污染普通 Order Client。

## 8. 影子预检

旧 settings 在 P3 阶段仍按旧 Order 检查决定是否阻断，同时 best-effort 调用新
Order `/precheck`，记录：

- `MATCH`
- `LEGACY_ONLY`
- `NEW_ONLY`
- `ERROR`

影子调用超时、5xx、空响应或 UNKNOWN 只能记录指标，不能改变旧路径返回。

## 9. 数据库文件

按顺序执行：

1. `order/src/main/resources/sql/order_account_lifecycle_p3_patch.sql`
2. `order/src/main/resources/sql/order_account_lifecycle_p3_backfill.sql`

回填后必须核对：

- passenger 未注销客户数量与 Order 投影数量。
- 是否存在缺失投影。
- Order 投影版本是否落后。
- 同版本 lifecycle status 是否不一致。

回填 SQL 的版本赋值必须最后执行，确保前面的条件表达式比较的是更新前目标版本。

## 10. 实施任务

### 任务 1：建立 passenger-api 动作权限矩阵

- 用 PathPattern 将稳定 HTTP 路径映射到动作码。
- NORMAL 与 restricted 使用同一策略组件裁决。
- 删除散落的受限路径字符串白名单。

### 任务 2：建立 Order 投影与写栅栏

- 增加 projection 和 event inbox。
- 实现版本、冲突、重复和乱序事件规则。
- 将创建订单等高风险写入接入 `AccountWriteFence`。

### 任务 3：实现 Order 生命周期参与者

- 建立预检、栅栏、最终检查和结果查询接口。
- 增加 participant inbox 和请求摘要。
- 对重复命令、摘要冲突、blocker 和事务回滚进行测试。

### 任务 4：接入影子预检和回填

- passenger-api 增加独立 Lifecycle Feign Client。
- 旧 settings 保持原裁决，只记录新旧差异。
- 提供 P3 Patch、Backfill 和覆盖率查询。
- 增加低基数指标和严格环境 Token 校验。

## 11. 验收矩阵

| 场景 | 预期 |
|---|---|
| ACTIVE + NORMAL 创建订单 | BFF 与 Order 都允许 |
| CANCELLING + restricted 创建订单 | BFF 403，直连 Order 409 |
| CANCELLING 查询、取消、支付欠款 | 允许，并继续校验订单归属 |
| Order 投影缺失或未知 | 高风险写入 503，失败关闭 |
| 旧版本或乱序投影 | 不覆盖新状态 |
| 下单先获得投影锁 | 订单成功，注销返回 BLOCKED |
| 注销先获得投影锁 | 下单被拒绝 |
| 同 Operation/Step/Hash 重放 | 返回既有参与者结果 |
| 同幂等键不同摘要 | 409，不改投影与 Inbox |
| 影子超时或差异 | 只记指标，不改变旧 settings |
| 内部 Token 缺失或错误 | 401/403 |

代码验证已经覆盖动作矩阵、投影版本规则、写门禁、参与者幂等、内部安全和影子比较。
P3 相关提交已完成；后续 P4/P5 均复用本阶段冻结的参与者契约。

## 12. 上线顺序

1. 执行 P3 Patch。
2. 执行 Backfill。
3. 执行覆盖率和版本一致性查询。
4. 配置 `ORDER_LIFECYCLE_INTERNAL_TOKEN`。
5. 部署 Order。
6. 保持写门禁在 SHADOW 或已确认的安全模式。
7. 部署 passenger-api 并观察影子差异。
8. 覆盖率和并发验证通过后再进入 ENFORCE。

## 13. 回滚与延期验证

可以关闭影子流量和 BFF 快速拦截，但领域高风险写门禁在投影成为权威后不能无条件关闭。
已写入的 projection、Inbox 和事件不得删除。

仍需在目标环境完成：

- 真实 MySQL 8 双连接行锁、死锁和隔离级别验证。
- P3 回填覆盖率和版本一致性核验。
- Kafka 投影发布、重试和对账由 P6 负责。

## 14. 完成定义

- BFF 动作码矩阵和 Order 领域写门禁都已生效。
- Order 投影不会被重复或乱序事件倒退。
- 参与者支持幂等命令、结构化 blocker 和结果查询。
- 并发下单与注销通过同一投影行锁串行化。
- 影子预检不改变旧路径裁决。
- P4/P5 得到稳定参与者契约。
