# 乘客账号生命周期 P6：可靠编排与恢复执行计划

> 当前状态（2026-07-27）：代码实现、P7 接口接入和五模块回归已完成；三个
> XXL-JOB Handler 已实现并完成本地注册配置检查。真实 Kafka/服务宕机演练、
> 调度告警阈值和生产运行证据仍属于上线验收项。

## 1. 本期目标

P6 把 P1～P5 已有能力接成一条可恢复的账号注销 Saga：

1. `passenger` 只按 Operation 创建时固化的 `account_lifecycle_step` 快照执行，不在运行中重新解释 YAML。
2. 同一 `sequence_no` 为一个执行组；组内步骤可以独立完成，下一组只能在当前组满足推进条件后开始。
3. 进入 `sequence_no=300` 前，在同一数据库事务中把 `irreversible_started` 从 `0` 改为 `1`。
4. 同步检查通过内部 HTTP 执行；异步动作由事务 Outbox 写入命令，再发布到 Kafka。
5. Kafka 回执丢失时，不重复猜测副作用结果，而是调用参与方结果查询接口恢复。
6. XXL-JOB 只负责触发恢复扫描，业务状态迁移仍由 `passenger` 编排服务完成。
7. 自动恢复耗尽后进入 `MANUAL_REVIEW`；人工恢复必须记录操作者、原因和审计事件。
8. Passenger 最终提交 `CANCELLED` 时在同一事务写状态事件 Outbox，由 Order、Calculate、Wallet
   各自幂等更新本地生命周期投影，避免下游永久停留在 `CANCELLING`。

## 2. 明确边界

- 不修改 `account-cancel-v1.yml`。
- 不新增生命周期业务表；P1 表结构已经具备编排、重试、Outbox 和审计字段。
- 不在 P6 切换旧 settings 注销入口；入口统一和灰度切流属于 P7。
- 不在 P6 清理旧 Redis key、旧接口或兼容代码。
- P5 SQL 仍由使用者按既定顺序独立执行，P6 不代为执行数据库脚本。
- 当前本地联调配置已默认开启 Kafka 发布与消费；测试 Profile 显式关闭，
  其他环境可通过 `ACCOUNT_LIFECYCLE_KAFKA_ENABLED` 或 Nacos 覆盖。

## 3. 状态推进规则

### 3.1 Operation

- `FENCED -> VALIDATING`：开始执行 `sequence=100` 最终检查。
- 任一 REQUIRED 检查返回 `BLOCKED`：Operation 进入 `BLOCKED`，持久化结构化 Blocker。
- 检查返回 `UNKNOWN`、超时或网络失败：步骤进入 `RETRY_PENDING`，Operation 进入 `RETRY_PENDING`。
- 当前组 REQUIRED 步骤全部成功：推进下一组。
- 进入 `sequence=300` 前：CAS 设置 `irreversible_started=1`，Operation 进入 `EXECUTING`。
- REQUIRED 动作重试耗尽：Operation 进入 `MANUAL_REVIEW`。
- `POST_ACTION` 失败：不回滚已完成注销，但保留步骤重试和诊断信息。
- `ACCOUNT_FINALIZE_CANCEL` 成功：Customer 与 Operation 在同一事务内完成最终状态提交。

### 3.2 Step

- 每次真实调用前写入 `RUNNING`、`attempt_count+1` 和 `timeout_at`。
- 成功写入 `SUCCEEDED`、`result_event_id/result_snapshot/completed_at`。
- 可恢复错误写入 `RETRY_PENDING/next_retry_at`，使用指数退避并设置上限。
- 回执消费必须比较 `operationNo + stepCode + commandEventId`；旧命令回执不得覆盖新尝试。

## 4. 参与方注册表

注册表集中维护：

- 参与方代码；
- 同步检查 URL；
- 动作 URL；
- 结果查询 URL；
- Kafka 命令目标域；
- 支持的稳定 step code。

启动时校验固化计划的所有远程 step 是否有唯一执行器。后续新业务只新增 Participant Adapter 和注册项，不把注销判断散落进普通业务 Service。

## 5. 可靠消息与恢复

### 5.1 命令 Outbox

- 创建异步命令和把 Step 置为 `RUNNING` 必须在同一事务。
- 发布器用短事务抢占 `PENDING/FAILED` 消息，Kafka ACK 后标记 `PUBLISHED`。
- 发布失败按指数退避回到 `FAILED`；超过最大次数进入人工诊断。
- `processing_at` 超时的记录可被恢复任务重新抢占。

### 5.2 参与方回执

- Calculate、Wallet Kafka 消费者按 `targetDomain` 过滤命令。
- 消费者调用 P4/P5 已有幂等 participant action；重复消息由 participant inbox 返回既有结果。
- 执行结果发布到统一结果 Topic；`passenger` 消费回执后推进步骤。
- 回执发布失败不影响领域事务正确性，Passenger 的结果查询恢复会读取 participant inbox 的稳定结果。
- `SESSION_CLOSE_WS` 使用广播语义：每个 Passenger API 实例使用独立 consumer group，
  关闭本节点内存会话；重复关闭安全且允许多节点重复回执。

### 5.3 主动查询

对超过 `timeout_at` 的 `RUNNING` 步骤：

1. 先调用参与方 `/results/{operationNo}/{stepCode}`。
2. 查到稳定结果则按结果收敛。
3. 404 说明命令尚未落地，可重新发布原幂等命令。
4. 查询失败按步骤退避，不直接判定业务失败。

## 6. XXL-JOB 与受控人工

提供三个幂等 Handler：

- `accountLifecycleOutboxPublishJob`：发布和恢复 Outbox。
- `accountLifecycleRecoveryJob`：恢复到期 Operation/Step。
- `accountLifecycleDiagnosticsJob`：输出积压、超时、人工态指标。

人工接口只允许：

- 重新调度；
- 接受参与方已有稳定结果；
- 对 POST_ACTION 标记人工完成；
- REQUIRED 步骤不得无证据强行成功。

每次人工动作写 `account_lifecycle_event`，包含 actor、reason、evidenceId，不记录敏感原文。
