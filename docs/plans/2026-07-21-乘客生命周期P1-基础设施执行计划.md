# 乘客账号生命周期 P1：基础设施执行计划

## 1. 阶段目标与状态

P1 负责建立换号、注销共用的生命周期内核，但不接管任何线上入口。

**当前状态：已完成。** `passenger_account_lifecycle_patch.sql` 已由用户执行；计划加载、
运行快照、状态机、持久化和 CAS 迁移均已进入后续 P2～P7 的实际链路。

本阶段只解决以下问题：

1. 生命周期计划如何定义、校验、版本化和固化。
2. 一次换号或注销如何形成 Operation、Step、Event 和 Outbox 运行快照。
3. 状态如何按白名单推进，并通过 `status + row_version` 防止并发覆盖。
4. 审计事实和待投递消息如何与业务事务一起提交或回滚。

## 2. 明确边界

- 新代码收束在 `com.sx.passenger.lifecycle`。
- 不新增公开 Controller，不修改旧 settings 的线上行为。
- 不执行订单、钱包、券积分等参与方动作。
- P1 的 Outbox 只负责可靠落库，不负责 Kafka 发布和恢复调度。
- YAML 随应用包发布，不允许热更新；已有版本不能原地覆盖。
- 数据库不保存计划定义表，只在 Operation 保存 `plan_digest`，在 Step 保存实际运行配置。

## 3. 数据库与配置

### 3.1 数据库增量

执行文件：

`passenger/src/main/resources/sql/passenger_account_lifecycle_patch.sql`

`customer` 增加：

- `lifecycle_status`
- `lifecycle_version`
- `auth_epoch`
- `current_lifecycle_operation_no`
- `cancelled_at`

新增六张运行表：

1. `account_lifecycle_operation`：一次换号或注销的聚合根。
2. `account_lifecycle_step`：Operation 冻结后的执行步骤。
3. `account_lifecycle_blocker`：订单、资金等结构化阻断项。
4. `account_lifecycle_event`：不可覆盖的状态与人工操作审计流水。
5. `account_lifecycle_outbox`：事务内可靠生成、事务外投递的消息。
6. `customer_phone_binding_history`：注册、换号和注销释放形成的手机号绑定事实。

明确不创建：

- `account_lifecycle_plan_definition`
- `account_lifecycle_plan_step_definition`
- `plan_snapshot`

### 3.2 生命周期计划

正式配置：

- `account-lifecycle/account-cancel-v1.yml`
- `account-lifecycle/phone-change-v1.yml`

加载时必须校验：

- schema、计划编码、版本和 operation type。
- Step 编码、顺序、参与方、阶段、执行模式和关键性。
- timeout 与 retry 范围。
- 注销必须且只能有一个最后执行的 `ACCOUNT_FINALIZE_CANCEL`。
- 换号必须且只能有一个身份提交步骤，且不能包含注销终结步骤。
- 同一 Operation Type 只能存在一个 ACTIVE 版本。

合法计划转换成规范 JSON 后计算 SHA-256，形成稳定的 64 位 `plan_digest`。

## 4. 状态机

### 4.1 Operation

`ACCOUNT_CANCEL` 支持请求、栅栏、校验、阻断、执行、重试、人工处理、完成和可撤销终态。
一旦 `irreversible_started=1`，不能再进入 `ABORTED`。

`PHONE_CHANGE` 只允许同步原子换号所需的前向路径，不能进入注销专用的
`FENCED/BLOCKED/ABORTED`。

`COMPLETED` 和 `ABORTED` 都是终态，不能迁出。

### 4.2 Step

Step 从 `PENDING` 开始；`SUCCEEDED/SKIPPED/CANCELLED` 为终态。
非法迁移必须在执行 SQL 前由纯状态机拒绝。

## 5. 实施任务

### 任务 1：建立 DDL、H2 Schema 和 YAML 资源

- 固化生产 SQL 和两个 v1 计划。
- 使 H2 测试 Schema 与 MySQL 字段和约束保持一致。
- 增加 DDL 静态契约测试，防止计划表或 `plan_snapshot` 回流。

### 任务 2：实现纯领域状态机

- 定义 Operation、Step 和相关枚举。
- 使用不可变白名单描述合法迁移。
- 覆盖终态迁出、不可逆后撤销、换号误入注销状态等非法场景。

### 任务 3：实现计划加载、校验和摘要

- 启动时一次性加载 classpath YAML。
- 任一计划非法时应用启动失败。
- 注册表和 Step 列表防御性复制，运行期不可修改。

### 任务 4：建立实体和 Mapper

- 映射 Operation、Step、Blocker、Event、Outbox、Phone Binding History。
- JSON 字段以字符串保存，避免 MySQL/H2 TypeHandler 差异。
- 不映射生成列 `phone_active` 和 `active_customer_id`。

### 任务 5：生成不可变运行快照

- 根据当前 ACTIVE 计划生成 Operation 和全部 Step。
- 同时生成 requested Event 与具备因果关系的 Outbox。
- 通用快照和消息中不得包含手机号、OTP、Token、密码等敏感原文。

### 任务 6：事务落库与 CAS 状态推进

- `LifecycleSnapshotStore.persistNew` 必须加入外层事务。
- Operation、Step、Event、Outbox 任一写入失败时整体回滚。
- 状态更新必须带当前状态和 `row_version`，更新数不是 1 时返回并发冲突。

- 边界扫描确认 P1 没有新增公开 Controller、Kafka 发布器、定时任务或 settings 接管。

## 7. 上线与回滚

上线顺序：

1. 执行并核对 `passenger_account_lifecycle_patch.sql`。
2. 部署包含 YAML 与 P1 内核的 passenger。
3. 验证两个 ACTIVE 计划加载成功。
4. 保持无公开入口、无编排执行。

P1 未接流量时可回滚应用版本，但不能随意删除已创建的表和审计数据。
一旦 P2 以后产生 Operation，数据库结构和历史事实只能做向前兼容变更。

## 8. 完成定义

- SQL、H2 Schema 与实体字段一致。
- 两个 v1 计划可以加载，非法计划阻止启动。
- Operation 只保存 digest，Step 固化实际配置。
- 四类核心运行记录能在同一事务提交或回滚。
- Operation 和 Step 迁移受状态机与 CAS 保护。
- 没有提前接管线上换号或注销入口。
