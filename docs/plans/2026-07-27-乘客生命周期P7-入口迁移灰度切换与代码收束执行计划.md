# 乘客账号生命周期 P7：入口迁移、灰度切换与代码收束执行计划

## 1. 目标

P7 负责把 P1～P6 已完成的生命周期能力正式接到乘客入口，并收走
`PassengerSettingsService` 中按业务域串行检查、清券和清积分的旧注销编排。

完成后：

1. 新生命周期 API 直接调用 passenger 的统一生命周期应用服务。
2. 旧 settings API 保持路径和基本请求兼容，但可按稳定灰度规则转调新流程。
3. 同一个客户始终命中同一路径；灰度比例变化只影响尚未受理的新请求。
4. 已经存在 Operation 的请求只能继续查询、重检、撤销或前向恢复，不能回落旧流程。
5. passenger-api 不再直接判断订单、钱包、券积分注销风险，也不直接执行清理。
6. 乘客只能查询属于自己的 Operation，内部人工恢复接口继续与公开查询隔离。

## 2. 安全默认与待定生产参数

- `PASSENGER_LIFECYCLE_ROLLOUT_ENABLED=false`
- `PASSENGER_LIFECYCLE_ROLLOUT_PERCENT=0`
- 新生命周期 API 始终使用新流程，不受旧入口灰度比例影响。
- 旧 settings 入口只有在开关开启且客户稳定分桶命中时才转调新流程。
- 生产切流比例和时间不是代码阻塞项，后续通过 Nacos 逐级设置
  `1 -> 5 -> 20 -> 50 -> 100`。
- 任何百分比回退只影响未创建 Operation 的新请求。

## 3. 对外契约

```text
POST /app/api/v1/account-lifecycle/cancellations
GET  /app/api/v1/account-lifecycle/operations/{operationNo}

POST /app/api/v1/account-lifecycle/phone-changes/sms/send
POST /app/api/v1/account-lifecycle/phone-changes
```

注销受理返回 `operationNo + status + lifecycleVersion + authEpoch`，HTTP 状态使用
`202 Accepted`。换号仍为同步原子事务，成功返回完成态 Operation 信息。

本期不开放管理员恢复能力给乘客端。撤销和重检只有在 passenger 已具备严格状态机、
所有权校验和审计事务后才开放，不能把现有内部运维接口直接映射为公开接口。

## 4. passenger 改造

1. 增加面向 BFF 的生命周期应用 Controller 和请求/响应 DTO。
2. 注销提交调用 `AccountCancellationFenceService`，成功建栅栏后触发
   `AccountCancellationOrchestrator.resume`。
3. 换号提交调用 `CustomerPhoneChangeService`。
4. Operation 查询按 `customerId + operationNo` 查询，返回脱敏的状态、步骤和 blocker，
   不直接暴露数据库实体、内部异常和请求快照。
5. settings 验证码发送继续复用已有 Purpose 隔离的 OTP 组件。
6. 为幂等键、生命周期版本、客户所有权和返回状态增加测试。

## 5. passenger-api 改造

1. 增加生命周期 Feign Client、公开 Controller、DTO 和应用 Service。
2. 从可信认证头取得 `customerId`，接收 `Idempotency-Key`、
   `expectedLifecycleVersion` 和 Request ID。
3. 新注销接口收到 FENCED 结果后关闭本节点普通会话，并返回受理信息。
4. 新换号接口成功后关闭本节点会话，要求重新登录。
5. 旧 settings 通过稳定客户分桶决定旧/新路径；记录 `operation + route + result`
   低基数指标。
6. 灰度命中新流程后，不再执行 BFF 旧订单分页、锁券判断、清券和积分清零。

## 6. 代码收束

- 删除 `PassengerSettingsService` 中旧注销编排实现：
  `loadAllPassengerOrders`、`hasActiveOrder`、`hasUnsettledOrder`、
  `hasLockedCoupon`、`tryInvalidateUnusedCoupons`、`tryClearBenefitPoints`。
- 旧逻辑在灰度期保留为独立 Legacy Adapter，不允许继续留在 settings 主服务。
- 灰度达到 100% 并稳定后删除 Legacy Adapter、旧领域 Client 依赖和影子比较入口。
- 使用代码扫描阻止 passenger-api 再出现注销后直接清券、清积分或分页查订单的分支。

## 7. 验证

- passenger：生命周期提交、幂等重放、所有权查询、脱敏视图。
- passenger-api：新 API 契约、202、稳定灰度、旧入口转调、未命中保持兼容。
- 回归：`passenger`、`passenger-api`、`order`、`calculate`、`wallet`。
- 静态扫描：旧编排方法、跨领域注销清理、敏感字段日志。
- 不执行 Docker/Testcontainers；真实 Kafka/MySQL 故障演练作为上线前运维验收。

## 8. 上线与回滚

1. 先部署 passenger，再部署 passenger-api；后端新接口验证通过后最后发布乘客 H5。
2. 保持旧入口灰度 0%，验证新 API 和 Operation 查询。注意新 Lifecycle API 不受旧
   settings 灰度控制，发布已迁移 H5 就代表该客户端直接切入新流程。
3. 按 `1 -> 5 -> 20 -> 50 -> 100` 调整旧 settings 灰度并观察状态停留、失败率和旧新差异。
4. 异常时关闭新受理或降低旧入口灰度；不得中止已经创建的 Operation。
5. 已受理 Operation 继续依赖 Outbox、Recovery 和人工处置前向收敛。
6. 100% 稳定后再删除 Legacy Adapter，不在首次部署时物理删除回滚通道。

   前向恢复，没有重新提交注销，也没有回落旧流程。
4. Wallet 解约、Calculate 券失效与积分清理命令经 Outbox/Kafka 重试成功，12 个
   Step 全部为 `SUCCEEDED`。
5. Operation `ALOb926440088f4459a8fd5fa45be4328b4` 最终为 `COMPLETED`；Passenger、
   Order、Calculate、Wallet 均收敛到 `CANCELLED / lifecycle_version=10`，客户

仍不等同于 Kafka 整体不可用/回执丢失演练，也不代表生产 `1→5→20→50→100` 灰度完成。
