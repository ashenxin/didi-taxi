# 乘客账号生命周期 P7 灰度切换与前向恢复手册

> 手册状态（2026-07-27）：代码和本地配置检查已完成，供部署、灰度与故障处置使用；
> 真实基础设施演练和生产灰度尚未签字完成。

## 1. 配置

旧 settings 入口的灰度由 passenger-api 配置：

```yaml
passenger:
  account-lifecycle:
    rollout:
      enabled: false
      percent: 0
```

对应环境变量：

```text
PASSENGER_LIFECYCLE_ROLLOUT_ENABLED
PASSENGER_LIFECYCLE_ROLLOUT_PERCENT
```

推荐在 Nacos 依次调整为 `1、5、20、50、100`。相同 customerId 使用稳定分桶，
同一比例下不会在旧新路径间随机跳动。

该开关只控制旧 settings 入口是否转调新流程。新的
`/app/api/v1/account-lifecycle/**` 接口始终走 Lifecycle 流程；已经迁移的乘客 H5
一旦发布，就不会因为旧入口灰度仍为 0 而回到旧编排。

## 2. 部署顺序

1. 确认 P1、P3、P4、P5 的 patch/backfill 已按各阶段计划执行并通过覆盖率核验；
   P6 没有新增 DDL，diagnostics SQL 仅为只读运维查询。
2. 确认 Kafka 三个 Topic、三个 XXL-JOB Handler 和参与服务内部 Token 正常。
3. 先部署 passenger。
4. 再部署 passenger-api。
5. 保持灰度关闭，验证新 `/app/api/v1/account-lifecycle/**` 接口。
6. 后端验证通过后再发布已迁移的乘客 H5；这一步会让该客户端直接进入新流程。
7. 开启旧 settings 灰度并从 1% 开始观察。

P7 没有新增表或字段，因此没有新的 DDL。

## 3. 每级灰度观察项

- `passenger.lifecycle.entry.requests{operation,route,result}`
- Operation 各状态数量及停留时间
- `BLOCKED`、`RETRY_PENDING`、`MANUAL_REVIEW` 数量
- Outbox 最老积压时长、失败和重试耗尽数量
- 参与服务 UNKNOWN、超时和 5xx
- 已 `CANCELLED` 但下游投影仍非 `CANCELLED` 的差异
- 旧入口与新入口的 409、503 比例

每一级至少覆盖一个完整业务观察周期；有异常时停止扩大比例。

## 4. 停止新受理

出现系统性异常时：

1. 将 `PASSENGER_LIFECYCLE_ROLLOUT_ENABLED=false`，停止旧 settings 新增灰度受理。
2. 在 gateway 临时关闭新的生命周期“提交”接口，但保留 Operation 查询、撤销和重检接口。
3. 不得停掉 Outbox 发布、Recovery 和 Diagnostics 任务。
4. 不得删除或修改已经存在的 Operation、Step、Event、Outbox。

## 5. 已受理 Operation 的处理

- `FENCED/VALIDATING/EXECUTING/RETRY_PENDING`：由 Recovery 前向推进。
- `BLOCKED`：向用户展示 blocker；解决业务义务后调用 recheck。
- `MANUAL_REVIEW`：使用内部人工恢复接口，必须填写 actor、reason、evidenceId。
- `irreversible_started=0` 且状态允许：用户可以 abort。
- `irreversible_started=1`：禁止撤销，只能重试、查询稳定结果或人工前向处理。
- `COMPLETED/ABORTED`：终态，不得重新执行领域副作用。

## 6. 回滚边界

允许回滚：

- 降低旧 settings 灰度比例。
- 关闭旧入口向新流程的转调。
- 停止接受新的生命周期提交。

禁止回滚：

- 降低 `auth_epoch`。
- 恢复已失效的普通 Token。
- 把已经创建 Operation 的请求重新交给旧注销分支。
- 强行把 REQUIRED 步骤标记成功。
- 删除 PENDING、PROCESSING、FAILED Outbox。

## 7. 旧代码最终删除条件

只有同时满足以下条件，才删除 `LegacyAccountCancellationAdapter`：

1. 灰度 100% 已稳定运行至少一个完整业务观察周期。
2. 没有未处理的新旧裁决差异。
3. Operation、Outbox、Recovery 和参与者结果查询指标稳定。
4. 故障演练证明 Kafka 不可用、回执丢失、服务重启均能恢复。
5. 已确认客户端能够处理 `operationNo + status` 和 HTTP 202。
